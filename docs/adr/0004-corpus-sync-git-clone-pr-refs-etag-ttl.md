# Синхронизация корпуса: полный git-клон + PR head refs, REST только для перечисления PR, свежесть через ETag + TTL

## Контекст

Recognition Bot ищет совпадения в корпусе = все форматы main + форматы, добавленные/изменённые в открытых PR (см. термины Corpus, Source в `CONTEXT.md`). Корпус должен отражать актуальное состояние GitHub, но при этом поиск обязан быть экономным: анонимный REST-лимит GitHub — 60 запросов/час, с токеном — 5000/час. Холодная сборка пофайлово — сотни запросов, пробивает лимит сразу. Стандартный аккаунт + токен; платные фичи недопустимы.

## Решение

**Транспорт контента — git, не REST.** Полный `git clone` main (репозиторий маленький — текстовые форматы), дальше `git fetch` дельтой. Содержимое открытых PR берётся через публикуемые GitHub git-ссылки `refs/pull/<N>/head` (`git fetch origin +refs/pull/<N>/head:refs/pr/<N>`). Git-протокол идёт по отдельным от REST лимитам, обновляется дельтой, а изменённые в PR файлы вычисляются локальным `git diff` (полный клон даёт merge-base) — ноль пофайловых REST.

**REST — только перечисление PR.** `GET /pulls?state=open` (≤40 PR влезают в одну страницу) — единственное, чего git не умеет: узнать, какие PR открыты, их заголовки и head SHA. Этот же ответ служит сигналом свежести набора PR.

**Свежесть — условные запросы + TTL, управляемые спросом.** Два условных REST-запроса по ETag на TTL-окно (ref main + список PR); 304-ответы не списываются с лимита. TTL 30–60 с: реальная частота изменения корпуса (часы/дни) на порядки больше TTL, так что устаревание ≤ TTL на практике не проявляется, а латентность и устойчивость к всплескам выигрываются постоянно. git-дельты тянутся только по изменившимся ref'ам. Проверка инициируется входящим запросом (не стоячим таймером) и только если истёк TTL — простаивающий бот не делает ни одной проверки.

Бюджет: холодная сборка ≈ 1 (enumeration) + git; установившийся режим — 2 условных запроса (оба 304) на TTL-окно.

## Альтернативы

- **Tarball (`GET /tarball/{ref}`)**: один запрос на весь main, но **полная** перекачка на каждое обновление вместо git-дельты; для PR всё равно нужен REST. Хуже для онгоинга.
- **Пофайловый REST контента**: сотни запросов на холодную, пробивает лимит.
- **HEAD-запросы для свежести**: тратят лимит и не дают дёшево понять, что именно изменилось; conditional GET по ETag строго лучше.
- **Проверка свежести на каждый SMS** (вместо TTL): максимальная свежесть ценой латентности и пачки запросов на всплесках — оптимизирует риск, которого на практике нет.

## Последствия

- Нужен read-only GitHub-токен (для git-аутентификации и подъёма REST-лимита на enumeration).
- Операционно: прунить локальные `refs/pr/<N>` при закрытии PR; фетчить head с `+` (force-update) на случай rebase/force-push в PR.
- Снапшот в памяти — производное от диск-клона; рестарт не требует re-clone (перечитать с диска + перекомпилировать). Re-clone только при стёртом диске. Рестарт не особый случай: на старте TTL-гейт открыт (`last-check-time` = «никогда»), поэтому первый же запрос после рестарта инициирует первую проверку свежести и догоняет main git-дельтой — без проактивного boot-пинка, пока отвечаем из диск-снапшота.
