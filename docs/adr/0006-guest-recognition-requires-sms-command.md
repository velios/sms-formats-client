# Guest-распознавание требует команды `/sms`; вызов без команды — тишина

## Контекст

В Guest-режиме (см. `CONTEXT.md` → «Guest-вызов») бот получает `guest_message`, только когда его явно позвали в чужом чате — упоминанием или reply. Сегодня **любой** такой вызов уходит в Recognition: `extractSms` (`bot/extract-sms.ts`) берёт текст reply или текст после упоминания как SMS, и бот отвечает. Из-за этого упоминание бота в разговоре — например, чтобы его **порекомендовать** («попробуй @zenmoneysms_bot, он распознаёт форматы») — заставляет бота влезть в чужой чат с распознаванием, обычно с «Похоже, нужен новый формат». Это шум ровно там, где нужна тишина.

Вокруг guest-пути уже выстроен инвариант «отвечать всегда, никогда не отдавать 500»: `answerGuestMessage` (`bot/answer.ts`) безусловно зовёт `answerGuestQuery`, а истёкший `guest_query_id` глушится, чтобы `webhookCallback` не вернул 500 и не вызвал head-of-line poisoning очереди вебхука. На этом фоне «осознанно промолчать» выглядит контринтуитивно — отсюда ADR.

Кроме того, пользователь может указать SMS **двумя способами одновременно** (reply на сообщение **и** текст после `/sms`), а в личке команда `/sms` сегодня не распознаётся вовсе — `extractDirectSms` считает SMS-ом весь текст целиком, поэтому `/sms <текст>` уехал бы в regex вместе с префиксом. Оба случая надо развести явно.

## Решение

Единый признак намерения распознать в Guest-режиме — команда `/sms`. В Direct-режиме команда **необязательна** (голый текст и так распознаётся), но если она есть — обрабатывается единообразно с guest. Полное дерево исходов:

### Guest-режим (распознавание требует `/sms`)

После снятия упоминания смотрим на остаток (trim):

- **Нет `/sms`** (с reply или без — неважно) → **тишина**: `answerGuestQuery` не вызывается, хендлер возвращается, вебхук отдаёт 200. Реакция на **отсутствие намерения** (про бота говорят, а не зовут распознавать). Reply без `/sms` тоже молчит — единое правило: guest-распознавание = упоминание/reply **плюс** `/sms`.
- **`/sms` + reply, payload после `/sms` пуст** → Recognition по тексту reply. При quote reply SMS — это **выделенный фрагмент** (`quote`), иначе весь текст `reply_to_message`. Здесь `/sms` — обязательный «спусковой» токен, источник один (reply).
- **`/sms` + payload, без reply** → Recognition по тексту после `/sms`.
- **`/sms` + reply + непустой payload** → **конфликт-подсказка**: SMS указан сразу двумя способами, бот не угадывает источник.
- **`/sms` без reply и без payload** (`@zenmoneysms_bot /sms`) → **guest usage-подсказка**. Реакция на **незавершённое намерение**: команду набрали, SMS не дали. Это не шум — человек сам обратился к боту.

Единственная рабочая форма guest-вызова — настоящее @упоминание бота (сущность `mention`) **плюс** `/sms` отдельным текстом: `@zenmoneysms_bot /sms <текст>` или reply на SMS + `@zenmoneysms_bot /sms`. Форма `/sms@zenmoneysms_bot` в guest **не поддерживается и не может поддерживаться**: в Telegram это единая сущность `bot_command` без сущности `mention`, а summon guest-бота идёт именно по `mention`/reply — значит `guest_message` вообще не доставляется, бот такого сообщения не видит.

### Direct-режим (`/sms` необязателен)

- **Голый текст** → Recognition по всему тексту (verbatim).
- **`/sms <текст>`** или **`/sms@zenmoneysms_bot <текст>`** → токен срезается, Recognition по `<текст>`. В личке `/sms@zenmoneysms_bot` и `/sms` равнозначны (в отличие от guest, здесь сообщение доставляется, так что обе формы обрабатываются).
- **`/sms` без текста** → **direct usage-подсказка**.
- **`/help`, `/start`** → direct usage-подсказка (служебные команды, не SMS).

### Правила матчинга токена `/sms`

`/sms` в **начале** остатка (для guest — после снятия упоминания и trim; для direct — после trim), **без учёта регистра**. Граница токена — **пробел или конец строки**: `/smskaspi` командой не считается (в guest → тишина, в direct → распознаётся как есть). Токен вырезается **до** нормализации/распознавания — ровно как упоминание, в regex не попадает. Суффикс `@zenmoneysms_bot` допускается только в direct.

### Подсветка вариантов команд

Делается **не** непрошеными ответами в чужой чат, а каналами, не зависящими от того, что бот молчит:

- **Описание профиля** (`setMyDescription`/`setMyShortDescription`) — видно на карточке бота, когда адресат рекомендации тапает по @упоминанию, ещё до Start.
- **Подсказки** — on-demand в самом чате (guest usage / direct usage / конфликт).
- **`setMyCommands`** с `/sms` — нативное меню. Полезно **только в личке**. В Guest-режиме бесполезно: документация не подтверждает, что `/`-меню показывается для бота, не состоящего в чате, а если бы и показывалось — оно вставило бы `/sms@zenmoneysms_bot`, форму, которая guest-бота не зовёт. На меню в чужом чате не закладываемся; discoverability там держится на описании профиля.

### Форма результата извлечения и схлопывание `respond`

Результат извлечения перестаёт быть «SMS или нет» и становится **discriminated union по исходу ответа** (вариант «извлекатель несёт готовый текст подсказки»):

```
type Intent =
  | { kind: "sms"; sms: string }
  | { kind: "hint"; text: string }   // текст подсказки кладёт извлекатель
  | { kind: "silent" };              // только guest
```

Поскольку union полностью кодирует исход, хвосты `respondToMessage` и `respondToDirectMessage` становятся идентичны и схлопываются в один `respond(intent, corpus): string | null` (см. «Альтернативы» → объединение точек входа). Различие guest/direct целиком уезжает в два извлекателя; `respond` остаётся mode-agnostic: `silent → null`, `hint → text`, `sms → renderResponse(recognize(...))`. `null` обрабатывает только guest-адаптер (direct silent не порождает).

## Альтернативы

- **На каждый вызов без команды отвечать списком команд.** Отвергнуто: это не убирает шум, а заменяет «нужен формат» на менюшку — в сценарии рекомендации бот всё равно влезает в чужой чат. Тишина — единственный исход, который реально решает исходную боль.
- **Триггер — жест reply (без токена).** Reply+упоминание само по себе распознаёт. Отвергнуто ради одного предсказуемого правила и потому, что рекомендация через reply тогда ломалась бы: единый признак намерения — `/sms`, и для reply тоже.
- **Любой ведущий слэш → подсказка** (`/help`, `/start`, и т.п.) в guest. Отвергнуто: снова приоткрывает дверь шума (`@bot /start` из любопытства вызовет реплику). В guest значим только `/sms`.
- **При конфликте (reply + payload) молча выбрать один источник.** Отвергнуто: бот угадывал бы намерение и мог распознать не то, что человек имел в виду. Явная подсказка дешевле молчаливой ошибки.
- **Извлекатель возвращает «тег» исхода, а текст подставляет `respond`/`render`.** Отвергнуто: guest- и direct-usage — разные строки при одном теге `usageHint`, что заставило бы либо плодить теги, либо протаскивать строку параметром в `respond`. Вариант «извлекатель несёт текст» оставляет `respond` тупым ценой того, что `extract` ссылается на готовые константы из `render`.
- **Оставить две функции `respond`.** Отвергнуто в паре с union: после добавления исходов `silent` и `conflict` хвост дублировался бы в большем объёме, а общий union делает схлопывание следствием, а не отдельной работой.

## Последствия

- **Конвейер ответа получает исход «не отвечать».** `respond` возвращает `string | null`; guest-адаптер при `null` — `return` без `answerGuestQuery`. Это **узкое, осознанное исключение** из инварианта «отвечать всегда»: head-of-line poisoning возникал из-за **ошибки отправки**, а не из-за **намеренного неотправления** — вебхук всё равно ack 200, очередь не застревает.
- **Две точки входа `respond` схлопываются в одну.** `respondToMessage`/`respondToDirectMessage` исчезают; адаптеры сами выбирают извлекатель и зовут общий `respond`. Схлопывание самих answer-адаптеров (cold-start/dry-run/send-политика) объявлялось **вне этого ADR**, но **сделано следом**: единый orchestrator `answer(intent, corpus, send)` в `bot/answer.ts` несёт инвариант «никогда не 500», dry-run и единственный try/catch, а guest/direct различаются только извлекателем и адаптером `Send { label, deliver }` за seam (`label` сохраняет в логе, какой путь упал). Заодно `respond` забрал cold-start и принимает `CompiledCorpus | null` (отдаёт `INITIALIZING_MESSAGE` при `sms` без снапшота), стаб `EMPTY_CORPUS` удалён, а `INITIALIZING_MESSAGE` переехал в `bot/render.ts` к остальным user-facing строкам.
- **Извлечение поддерживает quote.** Контракт входа получает `quote.text`; при quote reply он перебивает `reply_to_message.text`.
- **`USAGE_HINT` разделяется на три константы** (`bot/render.ts`): guest-usage (упоминает `/sms`), direct-usage (упоминает «просто текст» и необязательный `/sms`), конфликт. Direct-вариант не должен врать про упоминание/reply.
- **Изменение контракта «Guest-вызов» и «Личный вызов» в `CONTEXT.md`.** Формулировка «SMS — это текст reply либо текст после упоминания» перестаёт быть верной: guest-распознавание требует `/sms`, вызов без команды — тишина; в личке появляется необязательная `/sms`. Глоссарий обновляется **при имплементации**, не раньше.
- **Заметное изменение поведения для текущих пользователей.** Раньше reply на SMS + упоминание распознавал сразу; теперь нужен `/sms`. Об этом сообщают описание профиля и guest-подсказка.
- **Новый одноразовый сетап.** Регистрация команд и описания — отдельный `scripts/bot-set-profile.sh` (+ цель в justfile), рядом с `bot-set-webhook.sh`, а не внутри него: webhook-скрипт сам предостерегает от смешения концернов (ADR-0005).
