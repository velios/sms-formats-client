# Инвентарь банка: глубокий модуль `useBankInventory` — записи с двумерным статусом, добыча фактов снаружи

## Контекст

В `src/pages/BankWorkspace.tsx` (~3370 строк) ответ на вопрос «какие файлы есть в банке и что с каждым: изменён локально / создан / удалён / изменён в Source / не поддержан?» собирается из ~12 пересекающихся useMemo-множеств (`localChangedFormatFiles`, `localCreatedFormatFiles`, `visibleDeletedFormatFiles`, `sourceFileStatuses`, `unsupportedSourceFiles`, `allFormatFiles`, …) поверх внутренностей draftStore (`getChangedFiles`/`getDeletedFiles`/`drafts` дёргаются из ~6 мест), `activeSession.changedFiles`, source-стора и догрузки файлов PR. Интерфейс кластера равен его реализации:

- рендер файловой панели на каждый path делает четыре независимых lookup'а по разным множествам и сам собирает из них семантику индикатора (включая приоритет «локальное изменение глушит source-маркер»);
- senders.txt обслуживается параллельной парой флагов (`localSendersChanged`/`sourceSendersChanged`), считаемой из тех же входов отдельной строчкой;
- признак «создан локально» (`remoteContent === "" && !isDeleted`) и правило видимости удалённых (source-удаление скрывает файл, только если он не изменён локально) — знание, рассыпанное по вызывающему;
- `buildPublishFormatContents` **молча** выкидывает удалённые и не-формат файлы и при этом дублирует классификацию «формат ли это» (режет путь по `"/formats/"`), — вызывающий валидацию не знает, что фильтрация произошла;
- фолбэк-цепочка «откуда известны source-изменения» продублирована: `usePullRequestChangedFiles` внутри себя уже падает на store-список, а `effectiveSourceChangedFiles` поверх строит ту же лесенку ещё раз.

## Решение

Выделить фичу `src/features/bank-inventory/`: чистая сердцевина `buildBankInventory(факты) → инвентарь` плюс тонкий хук `useBankInventory`. Состояния у модуля нет — это чистая производная от чужих фактов; reducer/инъекции не вводятся.

Контракт шва:

- **Первичный шов — записи со статусом, не множества.** Инвентарь отдаёт упорядоченный список записей по **всем файлам банка**; каждая запись несёт класс (`format | senders | unsupported`) и статус в **двух независимых измерениях**: `local` (head-ref ↔ браузер: `created | changed | deleted | unchanged`) и `source` (origin/main ↔ head-ref по source ref редактора: `added | changed | deleted | unsupported | unchanged`, гранулярно — данные `file.kind` уже приходят, фиксируем бесплатно, хотя UI сегодня схлопывает всё в один жёлтый маркер). Теоретико-множественная арифметика, видимость удалённых и признак «создан» уходят в реализацию. Приоритет отрисовки («локальное глушит жёлтый») остаётся у панели: факты — знание инвентаря, что показывать при двух фактах — вкусовщина конкретной панели.
- **Выборки — только по именованному потребителю.** Помимо записей шов экспортирует считанные выборки, у каждой из которых есть реальный вызывающий: список формат-файлов с сортировкой «изменённые сверху» (поиск, rename, авто-выбор, интерсекции), пути для quick-check/интерсекций (живые форматы без видимо-удалённых), пути изменённых форматов для валидации, «живые формат-файлы с локальным содержимым» для bank-level валидации. Дисциплина: новая выборка попадает в шов только при именованном потребителе — дрейф обратно к «экспорту 12 множеств» запрещён этим пунктом.
- **Добыча фактов — снаружи.** Фолбэк-цепочка session → store → fetch PR-файлов и `isSelectionReady` — забота уровня сессии (пересечение с кандидатом «координатор workspace-сессии»), не инвентаря. Инвентарь принимает уже выбранный источник как записи единого типа с **опциональным `kind`**: сессия подаёт записи с типом изменения, фолбэки — без; деградация качества («changed, тип неизвестен») выражена прямо во входном типе, а не разруливается молча. Дублирование лесенки в `usePullRequestChangedFiles`/`effectiveSourceChangedFiles` схлопывается в одну чистую функцию снаружи (находка имплементации).
- **Publish-payload остаётся снаружи, валидационная выборка — внутри.** Разрез по знанию: `changedFilesForPublish`/`allChangedFilesForPublish` — pass-through над draftStore (deletion test проваливают, инвентарного знания ноль; второй к тому же кросс-банковый) — остаются у publish-потока. `buildPublishFormatContents` удаляется: его тихий фильтр становится **именем выборки** инвентаря («живые формат-файлы с локальным содержимым» — по построению без удалённых, без senders, без unsupported), классификация перестаёт жить в двух местах.
- **Охват — весь банк.** «Unsupported» — дополнение к классификации «формат»: вычислять его снаружи значило бы держать классификатор в двух местах. senders.txt — обычная запись класса `senders` (пара отдельных флагов исчезает). Инвариант модуля: у `unsupported`-записей local-измерение всегда `unchanged` (их нельзя редактировать в браузере) — гарантия инвентаря, а не память каждого потребителя. Раскладка списка (unsupported сверху, потом senders, потом форматы; поиск; вкладки) — у панели; инвентарь даёт факты и порядок внутри класса.
- **Хук подписывается на draftStore сам**, остальное — параметрами (`bankPath`, `sendersPath`, `bank.formatFiles`, source-записи). Шесть разрозненных чтений draftStore в `BankWorkspace` исчезают. Инъекций нет: асинхронщины и второго адаптера нет — один адаптер означает гипотетический шов.
- **Имя — `useBankInventory`** (Bank inventory, инвентарь банка): после решения «весь банк» имя «Format inventory» из обзора стало неточным, а «useBankFiles» прячет главное — статусы.

## Альтернативы

- **Минимальный интерфейс `files` + `statusOf(path)`.** Самый маленький шов, но publish/валидации/интерсекциям нужны выборки — им пришлось бы фильтровать по статусу на call site, set-арифметика вытекла бы обратно.
- **Экспорт готовых множеств (текущая форма, переехавшая в модуль).** Provably shallow: интерфейс из ~12 имён равен реализации, deletion test проваливается, семантика «что с файлом» по-прежнему собирается потребителем из четырёх lookup'ов.
- **Один enum статуса вместо двух измерений.** Файл бывает одновременно изменён локально и в source; схлопывание заставило бы инвентарь решать приоритет отображения — UI-политику панели.
- **Фолбэк-цепочка внутри инвентаря (вплоть до fetch).** Модуль перестаёт быть чистой арифметикой (загрузка, «ещё грузится», отмена), а кандидат «координатор сессии» потом выдирал бы добычу обратно.
- **Publish-payload внутрь инвентаря.** Pass-through над draftStore без инвентарного знания; кросс-банковый `allChangedFilesForPublish` растягивал бы охват модуля за пределы банка.
- **Охват «только Format-файлы».** Классификатор «формат / не формат» понадобился бы и снаружи (для unsupported) — два места в день рождения модуля; панель потребляла бы инвентарь плюс два самодельных механизма рядом.
- **Инъекция draftStore-чтения.** Тестовая гипотеза без второго адаптера; чистая сердцевина и так покрывает арифметику без рендера.

## Последствия

- `BankWorkspace` теряет блок из ~12 useMemo, шесть чтений draftStore, пару senders-флагов и хелперы `collect*`/`buildPublishFormatContents`; рендер панели читает один статус записи вместо четырёх множеств.
- Правила «source-удаление видно, только если файл не изменён локально», «created = пустой remoteContent без удаления», «unsupported не редактируется» тестируются чистой функцией в одном месте.
- Гранулярные source-статусы зафиксированы в типе уже сейчас; UI продолжает схлопывать их в жёлтый маркер — расширение отображения, если понадобится, не потребует менять шов.
- Поведенческих диффов нет — рефакторинг byte-for-byte; единственное видимое глазами изменение это его отсутствие.
- Находка для имплементации: схлопнуть продублированную фолбэк-лесенку (`usePullRequestChangedFiles` против `effectiveSourceChangedFiles`) в одну чистую функцию снаружи инвентаря.
- CONTEXT.md не правится до имплементации; при имплементации — добавить статьи «Bank inventory» и отсутствующую «Bank», и развести два смысла «источника»: Source (термин бота: происхождение распознанного формата) против source ref редактора (origin/main ↔ head-ref) — например, статьёй «Source ref (источник правок)».
