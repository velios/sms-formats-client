# Recognition Bot живёт в том же репозитории и импортирует только `@/domain/format`

## Контекст

Нужен Telegram-бот, который по входящему SMS возвращает распознающие его форматы (см. термин Recognition Bot в `CONTEXT.md`). Он обязан переиспользовать ту же операцию Recognition, что и редактор: ядро распознавания должно оставаться байт-в-байт идентичным мобильному приложению Zenmoney (см. ADR-0001), и любая вторая копия логики матчинга — это второй способ разъехаться с устройством. Репозиторий сейчас фронтенд-only (Vite/React, без бэкенда); бот — первый серверный код здесь.

## Решение

Бот — отдельное bun-приложение **в этом же репозитории** (например, папка `bot/`), переиспользующее recognition-ядро прямым импортом барреля `@/domain/format`. Дисциплина: бот импортирует **только** этот баррель и **никогда** не делает deep-import других файлов `src/`. Баррель трактуется как публичный API ядра по соглашению.

## Альтернативы

- **Bun workspace, выделить `packages/recognition`**: чистая граница, но это преждевременный и рискованный рефакторинг работающего фронтенда (переписать все импорты `@/domain/format`, перестроить Vite/vitest/biome) ради выгоды, которой у бота пока нет. Апгрейд до workspace остаётся механическим именно потому, что поверхность уже один баррель.
- **Отдельный репозиторий с публикацией пакета**: максимальная развязка, но возвращает рассинхрон версий — главный риск для ядра, обязанного совпадать с устройством. Запиннить старую версию recognition = тихо разойтись с продакшеном.

## Последствия

- Бот зависит от пути внутри `src/` фронтенда; рефакторинг `src/domain/format/` может его задеть — граница держится соглашением, а не пакетом.
- `package.json` смешивает React-devDeps с runtime-зависимостями бота (grammY, сервер). Косметика.
- Деплой всё равно раздельный: фронтенд — статика за Caddy, бот — долгоживущий процесс (отдельный systemd-юнит). «Тот же репо» не означает «тот же деплой-юнит».
