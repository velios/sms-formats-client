# Чем рисовать «было → стало» на экране импорта

Записка к [#24](https://github.com/velios/sms-formats-client/issues/24) (карта [#22](https://github.com/velios/sms-formats-client/issues/22)). Вопрос: чем показывать предлагаемые агентом изменения тела формат-файла, если тело — это одна строка regex на 200–300 символов плюс секции `-----COLUMNS-----` / `-----EXAMPLE-----`, и построчный diff на таком материале нечитаем.

**Статус фактов.** Версии и метаданные пакетов получены командами (команда указана рядом с числом) 2 августа 2026. Поведение алгоритмов — не пересказ README, а замер: скрипт гоняли на настоящей паре «было → стало» (см. «Замер на реальном материале»). Устройство `@codemirror/merge` читалось по опубликованному `dist/index.js` и `dist/index.d.ts` версии 6.12.2, а не по документации.

---

## Материал, который надо показать

Реальная пара из корпуса АТБ (`~/Downloads/output_corpus.txt` — ответ модели; «было» вытащено из `zenmoney/sms-formats` через `gh api repos/zenmoney/sms-formats/contents/…`), файл `src/АТБ-ru_4679/formats/Оплата р Карта https link atb su history_9190.txt`:

```
было:  .*?[Оо]плат\w*\s+([0-9][\d\s.,]*\d)\s*([^\d\s]{1,3})\.?\s+.*?(?:Карта|Card).*?\*(\d{4})
стало: ^(?:Оплата|Покупка|Списание)\s+(\d[\d\s.,]*[.,]\d{2})\s+(\S+)\s+Карта\s+\*(\d{4})(?:\s+.*)?$
```

87 и 92 символа в одной строке; плюс к телу добавился целый блок `-----EXAMPLE-----`. Построчно это «строка 1 изменилась, строк 8–9 добавлено» — формально верно, читать нечего.

**Важная деталь про существующий редактор.** `UnifiedRegexEditor` — однострочный: в его документе лежит **только regex** (`singleLineFilter`, `src/features/regex-lab/UnifiedRegexEditor.tsx:548`), а `COLUMNS` и `EXAMPLE` живут отдельным React-состоянием и рисуются `Textarea` (`src/features/format-editor/FormatEditor.tsx`). То есть «показать тело файла целиком» — это документ, которого сегодня в редакторе не существует ни в каком виде.

## Замер на реальном материале

Скрипт считал, на сколько изменённых кусков каждый кандидат режет ту же пару файлов целиком. Меньше кусков при сохранении смысла = читаемее; «конфетти» из двух десятков кусков в 90-символьном регэкспе не читается.

| Кандидат / режим | изменённых кусков на файл |
|---|---|
| `@codemirror/merge` → `presentableDiff` | **8** |
| `@codemirror/merge` → `diff` (сырой) | 15 |
| `jsdiff` → `diffChars` | 22 |
| `jsdiff` → `diffWordsWithSpace` | 22 |
| `jsdiff` → `diffLines` | 3 (но это и есть бесполезный построчный) |
| `diff-match-patch` → сырой `diff_main` | 22 |
| `diff-match-patch` → `diff_cleanupSemantic` | 3 |
| `diff-match-patch` → `diff_cleanupEfficiency` | 16 |
| `fast-diff` | 22 |

Числа «3» обманчивы. `diff_cleanupSemantic` на этой паре схлопывает всё в «удалили весь старый regex, вставили весь новый» — ровно тот исход, ради ухода от которого затевалась задача: семантическая чистка diff-match-patch настроена на прозу, а не на регэксп. `diffLines` — определение построчного diff.

Что реально выдаёт `presentableDiff` на этой паре (`A[…]` → `B[…]`):

```
".*?[Оо]"            -> "^(?:О"
"\w*"                -> "а|Покупка|Списание)"
"[0-9]"              -> "\d"
"\d"                 -> "[.,]\d{2}"
"*([^\d\s]{1,3})\.?\s+.*?(?:" -> "+(\S+)\s+"
"|Card).*?"          -> "\s+"
""                   -> "(?:\s+.*)?$"
""                   -> "\n-----EXAMPLE-----\nПокупка 699.00 RUR Карта *4383 …\n"
```

Это читаемо: видно, что якорь появился, альтернатива расширилась, класс символов заменён на `\S+`, добавлен хвост и новый пример. Остальные кандидаты на том же входе дают либо это же, но разорванное на 22 куска, либо «всё заменено».

Причина не магическая, она записана в API: `presentableDiff` описан в `dist/index.d.ts` как «Compute the difference between the given strings, and clean up the resulting diff for presentation to users by **dropping short unchanged ranges, and aligning changes to word boundaries** when appropriate». У jsdiff, diff-match-patch и fast-diff аналога, настроенного под показ, нет — есть либо сырой посимвольный результат, либо чистка под прозу.

## 1. Внутристрочность

Внутристрочность умеют **все четыре** кандидата — это не различитель. Различитель — качество группировки (таблица выше).

- **`@codemirror/merge`.** Двухуровневая модель: `Chunk` — диапазон изменённых строк, `Chunk.changes` — «The individual changes inside this chunk», посимвольные `Change` с координатами `fromA/toA/fromB/toB` (`dist/index.d.ts`). В отрисовке `buildChunkDeco` (`dist/index.js:804`) идёт по строкам чанка и внутри каждой навешивает `Decoration.mark({class: "cm-changedText"})` на пересечение строки с изменением — то есть подсветка именно внутри длинной строки, поверх целиком помеченной `<ins>`/`<del>` строки. У unified-режима есть отдельная опция `allowInlineDiffs`: «chunks that look like they contain only inline changes will have the changes displayed inline, rather than as separate deleted/inserted lines» (`dist/index.d.ts`).
- **`diff` (jsdiff).** `diffChars` / `diffWords` / `diffWordsWithSpace` — посимвольные и пословные токенизаторы, ограничения «только строки» нет ([README](https://github.com/kpdecker/jsdiff)). Отдаёт массив `{value, added, removed}`; отрисовка — целиком на нас.
- **`diff-match-patch`.** Посимвольный `diff_main` — библиотека изначально про diff внутри строк. Есть `diff_prettyHtml` (`index.js:1241`), но это `<ins style="background:#e6ffe6">` c инлайновыми стилями — в наш визуальный язык не годится.
- **`fast-diff`.** Один посимвольный `diff(a,b)`, вырезанный из diff-match-patch. Ровно тот же сырой результат без чистки.

## 2. Что даёт `@codemirror/merge` и переиспользует ли он нашу подсветку

Два режима (`dist/index.d.ts`):

- **`MergeView`** — два редактора рядом. Конструктор принимает `a: EditorStateConfig` и `b: EditorStateConfig`, то есть **обе стороны конфигурируются нашими расширениями**: `baseTheme`, `tokenDecoField`, `tokenDecorations` из `UnifiedRegexEditor.tsx` встают в обе стороны как есть. Здесь ответ «да, тот же визуальный язык» — но с ценой, см. ниже.
- **`unifiedMergeView`** — одно поле, удалённые куски рисуются виджетами над новым текстом. Здесь ответ **«нет»**: подсветка удалённой стороны в `dist/index.js:1577` делается как `let lang = syntaxHighlightDeletions && state.facet(language)` и дальше `highlightTree(...)` из `@lezer/highlight`. Она завязана на lezer-язык, которого у нас нет: наша раскраска regex — не язык, а `EditorView.decorations.compute` над собственным `tokenDecoField`, наполняемым нашим токенизатором (`UnifiedRegexEditor.tsx:394`, план строит `buildPatternHighlightPlan` из `src/domain/format/pattern-highlight.ts`). Документация опции `syntaxHighlightDeletions` это и признаёт честно: «By default, deleted chunks are highlighted using the main editor's language. Since these are just fragments, not full documents, this doesn't always work well» (`dist/index.d.ts:339`).

Цена варианта `MergeView`, если брать его всерьёз:

1. Всё, что красит regex, — **module-private** в `UnifiedRegexEditor.tsx`: экспортируется только React-компонент (`export const UnifiedRegexEditor`, строка 635), а `tokenDecoField`, `tokenDecorations`, `baseTheme` наружу не выходят. `MergeView` создаёт свои `EditorView` сам и существующий вью принять не может — значит нужен рефакторинг: вытащить набор расширений в отдельный модуль.
2. Токены в поле попадают **эффектами из React** (`setTokenDecoEffect`, строка 215) после монтирования. Для merge-вью их придётся считать и диспатчить в обе стороны.
3. Документ редактора сегодня — только regex, однострочный. Diff тела файла целиком (regex + `COLUMNS` + `EXAMPLE`) — другой документ; наша раскраска покроет только первую строку, секции останутся простым текстом (что, возможно, и правильно).
4. `MergeView` выравнивает строки по вертикали замерами высот; при `EditorView.lineWrapping` (а он у нас включён, строка 779) 300-символьная строка переносится, и выравнивание двух колонок на переносах заведомо приблизительное.
5. Merge-вью тащит с собой UI мержа — `revertControls`, `mergeControls` (accept/reject по чанкам). Решение #3 карты — импорт целиком, без пофайловых галочек и подавно без почанковых; эти кнопки надо гасить (`mergeControls: false`, `revertControls` не задавать), иначе интерфейс обещает то, чего продукт не делает.

Отдельно ценно и без всего вью: `presentableDiff` и `diff` **экспортируются пакетом как чистые функции** — их можно взять как алгоритм и рисовать самим, не поднимая `MergeView`.

## 4. Случаи без тела: новый файл и `<delete>`

Замер поведения на пустой стороне:

- `presentableDiff("", b)` → `[{fromA:0, toA:0, fromB:0, toB:289}]` — одна вставка на весь документ;
- `presentableDiff(a, "")` → `[{fromA:0, toA:209, fromB:0, toB:0}]` — одно удаление;
- `jsdiff.diffChars("", b)` → одна часть `{added:true, len:289}`;
- `diff_match_patch.diff_main("", b)` → `[[1, 289]]`.

Вывод одинаков для всех: **ни один кандидат ничего не даёт для этих случаев**. Все честно отвечают «всё добавлено» / «всё удалено», и это ровно та информация, которую мы и так знаем до вызова diff — из `DraftEntry.remoteContent === undefined` и `DraftEntry.isDeleted` (`src/store/index.ts:55`, факты карты #22). Показ нового файла и показ удаления рисуются отдельно при любом выборе кандидата: у нового файла интересен не diff, а само тело с раскраской, у удаления — путь и причина из `<delete>`. Гонять diff по пустой строке — лишний шаг.

Если всё же взят `MergeView`, пустая сторона — это пустой редактор рядом с полным: технически работает, визуально это дыра, которую всё равно захочется заменить плашкой.

## Вариант «ничего не берём»

Оценивать его честно: два тела рядом с существующей regex-раскраской. Раскраска для этого уже готова и не привязана к CodeMirror — `buildPatternHighlightPlan(regex, …)` из `src/domain/format/pattern-highlight.ts` — чистая функция «строка → план подсветки», её уже зовёт `RegexLab.tsx:296`. То есть нарисовать два тела в фирменных цветах можно сегодня, нулевой ценой в байтах.

Чего этот вариант не даёт: показать **что именно** поменялось. Замер выше — прямое свидетельство, что на 90-символьном регэкспе глазом это не берётся: изменений восемь, они разбросаны по всей строке, и половина из них — односимвольные (`[0-9]` → `\d`). Человек на экране импорта должен решить «принимать ли предложение агента»; два похожих регэкспа рядом этого решения не поддерживают. Именно это и говорит решение #4 карты: ценность создаёт хороший показ изменений, а не гейт.

Так что «ничего не берём» здесь стоит не ноль, а «экран импорта делает вид, что показывает изменения». Отвергается — но не из-за зависимостей, а по существу задачи.

## Рекомендация и её цена

**Взять `@codemirror/merge`, но только как алгоритм: `presentableDiff`. Отрисовку сделать своими средствами — двумя колонками или одним потоком, поверх существующей regex-раскраски. `MergeView` / `unifiedMergeView` не поднимать.**

Почему так:

- `presentableDiff` — единственный из проверенных, кто на нашем реальном материале даёт читаемую группировку (8 осмысленных кусков против 22 «конфетти» или 3 «всё заменено»). Это замер, а не обещание README.
- Пакет не тащит ни одного нового npm-пакета: все его зависимости уже в `bun.lock`.
- Он живой (6.12.2 от 2026-06-09), и это единственный живой кандидат с чисткой diff под показ человеку.
- Отказ от `MergeView` снимает всю пятёрку издержек из пункта 2: не нужен рефакторинг приватных расширений редактора, не нужно дублировать диспатч токенов, не воюем с выравниванием переносимых строк, не гасим чужие accept/reject-кнопки, не упираемся в lezer-подсветку удалённой стороны.
- `Change` — это просто четыре смещения (`fromA/toA/fromB/toB`). Наложить их на тот же план подсветки, который уже строит `buildPatternHighlightPlan`, — арифметика по диапазонам, без нового визуального языка.

**Цена рекомендации:**

1. **Отрисовку пишем сами.** `presentableDiff` отдаёт координаты, не DOM. Нужен компонент, накладывающий два набора диапазонов (изменения и токены regex) на одну строку. Это работа, которой при `MergeView` не было бы, — но при `MergeView` вместо неё была бы работа по пунктам 1–5 выше, и результат был бы в чужом визуальном языке.
2. **Тянем весь пакет ради одной функции.** 11.7 KB gzip — верхняя граница; сколько именно останется после tree-shaking вью-части, надо мерить на настоящем vite-бандле, а не верить оценке. Если окажется, что пакет не шейкается, честная развилка — либо принять 11.7 KB, либо переписать чистку самим поверх `fast-diff` (3.3 KB), что уже полноценная своя работа.
3. **Зависимость от подчинённого пакета.** `@codemirror/merge` живёт в ритме CodeMirror и вне GitHub; issue по нему заводить в чужом трекере на `code.haverbeke.berlin`. Риск невелик — берём чистую функцию с узким контрактом (две строки → массив четвёрок), заменяемую на любую другую.
4. **Случаи без тела всё равно рисуем отдельно.** Новый файл и `<delete>` diff не касаются; это отдельные состояния экрана, и они не входят в выигрыш от рекомендации.
5. **Тела целиком vs. только regex.** Diff считается по телу файла целиком, а regex-раскраска сегодня умеет только regex-строку. Секции `COLUMNS` / `EXAMPLE` в показе будут diff'ом без раскраски. Это скорее правильно, но решить это явно надо на этапе PRD.
