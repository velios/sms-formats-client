# Инвентарь правил для `format-rules.md`

Исследование по issue #13 (карта #11, решение 2: единый человекочитаемый документ правил, который читает и человек в приложении, и агент в собираемом промте).

**Что это.** Перечень правил-кандидатов в новый `format-rules.md` с источником каждого (файл:строка) и пометкой, покрыто ли правило в `src/content/cookbook.md`. Сам текст документа здесь не пишется.

**Источники** — только этот репозиторий: `src/domain/format`, `src/domain/validation`, `src/domain/types.ts`, `src/features/bank-inventory`, `src/features/publish-panel`, `src/pages/BankWorkspace.tsx`, `CONTEXT.md`, `docs/adr/`, `src/content/cookbook.md`, `src/i18n/*.json`.

## 0. Граница между документами

| | `cookbook.md` (вендоренный снапшот) | `format-rules.md` (новый) |
| --- | --- | --- |
| Предмет | **Содержимое** regex: как писать паттерн под сущность | **Оболочка**: структура файла, колонки как контракт, файлы и правила уровня банка |
| Вопрос | «Каким должен быть паттерн для суммы?» | «Из чего состоит файл формата и что запрещено внутри банка?» |
| Владение | Апстрим `zenmoney/sms-formats`, правится только через чужой PR (карта #11, Out of scope) | Наш репозиторий, правим свободно |
| Аудитория | Оператор, пишущий regex | Оператор + агент, которому надо понять формат файлов банка целиком |

Практическое правило демаркации: **если правило можно проверить, не разбирая семантику regex, — оно в `format-rules.md`.** Всё, что требует рассуждения «этот паттерн правильно ловит сумму» — в cookbook.

Единственная зона нахлёста — колонки: cookbook разбирает колонки как *сущности* (какой сниппет под `income`), `format-rules.md` должен дать колонки как *контракт файла* (закрытый список имён, синтаксис `#`, соответствие числу групп). Дублирования нет, если `format-rules.md` не повторяет сниппеты, а cookbook не повторяет список допустимых имён.

Легенда пометок:
- **cookbook: нет** — правила в cookbook нет, это чистый кандидат в `format-rules.md`;
- **cookbook: есть** — покрыто, в `format-rules.md` не тащим (максимум ссылка);
- **cookbook: косвенно** — упомянуто вскользь, в другом контексте; формулировать заново придётся, но с оглядкой.

## 1. Структура файла формата

Файл формата — это plain text из трёх видов блоков: regex, секция колонок, одна или несколько секций примеров. Разбор — `src/domain/format/parser.ts`, канонический вид — сериализатор там же.

| # | Правило | Источник | cookbook |
| --- | --- | --- | --- |
| F1 | Разделители секций — ровно строки `-----COLUMNS-----` и `-----EXAMPLE-----`; распознаются по `line.trim()`, то есть ведущие/хвостовые пробелы вокруг маркера допустимы | `src/domain/format/parser.ts:3-4`, `parser.ts:9`, `parser.ts:117` | нет |
| F2 | Regex — это всё, что идёт **до** `-----COLUMNS-----`, и обрывается на первой пустой строке; то есть regex может занимать **несколько строк** (склеиваются через `\n`) | `src/domain/format/parser.ts:32-41` | нет |
| F3 | Файл без `-----COLUMNS-----` не разваливается: за regex берётся первая строка, но выдаётся ошибка `MISSING_COLUMNS` | `src/domain/format/parser.ts:22-30` | нет |
| F4 | Пустой regex — ошибка `MISSING_REGEX` («Missing regex (first line)») | `src/domain/format/parser.ts:121-128` | нет |
| F5 | Колонки — **одна строка сразу после** маркера `-----COLUMNS-----`, имена разделены `;`, пробелы вокруг имени срезаются, пустые элементы отбрасываются (значит хвостовой `;` безвреден) | `src/domain/format/parser.ts:43-53` | нет |
| F6 | Секций `-----EXAMPLE-----` может быть много; каждая тянется до следующего маркера (`EXAMPLE` или `COLUMNS`) или до конца файла | `src/domain/format/parser.ts:66-108` | нет |
| F7 | Внутри примера пустые строки по краям срезаются, **внутренние переносы сохраняются** — пример может быть многострочным | `src/domain/format/parser.ts:55-64`, `parser.ts:80`; термин Example — `CONTEXT.md:33-34` | косвенно (cookbook.md:25 — про схлопывание при матче, не про хранение) |
| F8 | Пустая секция примера (после срезки ничего не осталось) молча выбрасывается из списка примеров | `src/domain/format/parser.ts:104-106` | нет |
| F9 | Файл без единой секции `-----EXAMPLE-----` — ошибка `MISSING_EXAMPLE` | `src/domain/format/parser.ts:89-97` | нет |
| F10 | Канонический порядок при записи: regex → пустая строка → `-----COLUMNS-----` → строка колонок → (пустая строка → `-----EXAMPLE-----` → текст примера)\* → завершающий `\n` | `src/domain/format/parser.ts:139-157` | нет |
| F11 | Шаблон нового файла: `^(.*)$` + колонка `comment` + пример `Sample SMS text` | `src/domain/format/parser.ts:162-166` | нет |

**Замечание к F2.** Многострочный regex — следствие реализации, а не задекларированное правило: строки склеиваются через `\n`, при этом сам `\n` попадёт в паттерн литералом. Требует решения (см. §7, G6).

## 7. Чего нигде нет — требует решения человека

Каждый пункт: что не определено, почему всплыло, чем это грозит документу.

**G1. Содержимое `senders.txt` не описано и не валидируется нигде.** Единственная формулировка — подсказка в UI (`src/i18n/ru.json:141`): «один на строку, пустые строки допускаются, строки с `#` тоже отправители». Не определено: чувствительность к регистру, допустимы ли дубликаты, есть ли требования к виду идентификатора (короткий номер vs буквенное имя), нормализуются ли пробелы, нужен ли завершающий перевод строки, должен ли файл быть непустым (`MISSING_SENDERS` ловит только отсутствие файла — `validation/index.ts:131`). Если `format-rules.md` должен объяснить `senders.txt` агенту, всё это надо решить.

**G2. Правило именования файлов форматов.** Код требует только «внутри `formats/`, оканчивается `.txt`» (`file-path.ts:1-3`). UI подсказывает `format_name` + числовой суффикс (`CreateFormatModal.tsx:36-39`, placeholder `format_name`), но не проверяет ни регистр, ни алфавит, ни осмысленность имени, и не объясняет, что означает суффикс `_N` (для папки банка это `bankId` — `client.ts:1443`; для файла формата семантика не зафиксирована нигде). Нужно решение: описываем как соглашение, описываем как «свободно» или не описываем вовсе.

**G3. Расхождение по параметру `syncid`.** `src/domain/types.ts:126-132` объявляет `syncid` параметризованной с подсказкой `ccard / checking / deposit`; cookbook (`cookbook.md:143`) знает только `syncid#cash`. Что из этого — актуальная практика, из репозитория не следует. Аналогично `date`: `types.ts:122` даёт `paramHint: "dd.MM.yyyy"`, cookbook (`cookbook.md:164`) называет ровно эту форму легаси и требует order-based `date#dMy`. Кандидат в `format-rules.md` — таблица «какие параметры после `#` легальны», но её содержимое надо сначала утвердить.

**G4. Пустая строка колонок — легальный случай или дефект?** Парсер и валидатор её пропускают (`validation/index.ts:39`), cookbook (`cookbook.md:278`) описывает OTP/failed-форматы с пустыми колонками как отдельный класс, на который правила транзакционного regex не распространяются. Но нигде нет определения этого класса как *класса файла*: как его отличить от обычного формата, какие правила к нему применимы, надо ли на него распространять запрет пересечений (X1). Для агента это существенно: без явного правила он либо примет пустые колонки за ошибку, либо начнёт их плодить.

**G5. Синтаксис `/pattern/flags`.** Cookbook (`cookbook.md:24`) сообщает, что апстрим-исполнитель поддерживает `/pattern/flags` (`i,u,m,s`) и инлайн `(?i)`. Редактор такого синтаксиса не разбирает: `tryCompile` (`regex.ts:93-119`) отдаёт строку в `new RegExp` как есть, то есть `/.../i` станет литеральными слэшами. Не решено, писать ли в `format-rules.md` «этот синтаксис существует, но не используем» или умолчать. Умолчание оставляет агенту грабли: сгенерированный `/…/i` пройдёт локальную валидацию как «просто не матчится».

**G6. Многострочный regex.** Парсер (`parser.ts:32-41`) разрешает regex занимать несколько строк до первой пустой и склеивает их через `\n`. Ни одного слова об этом ни в CONTEXT.md, ни в cookbook. Непонятно, поддерживает ли это апстрим-исполнитель и является ли это фичей или толерантностью парсера. Требуется решение до того, как правило попадёт в документ, который читает агент.

**G7. Правила по примерам как данным.** Не зафиксировано: минимальное/максимальное разумное число примеров (парсер требует ≥1 — `parser.ts:89-97`), должны ли примеры быть реальными SMS, обязательна ли анонимизация персональных данных (номера карт, суммы, имена), можно ли брать один и тот же пример в двух форматах. Это правила уровня файла и они естественно ложатся в `format-rules.md`, но источника для них в репозитории нет вообще.

**G8. Порядок секций внутри файла.** Сериализатор задаёт канонический порядок (`parser.ts:139-157`), но парсер терпит и другие: `-----EXAMPLE-----` до `-----COLUMNS-----`, несколько блоков вперемешку. Не решено, объявлять ли канонический порядок обязательным (тогда это правило + потенциальная новая проверка) или зафиксировать текущую терпимость.

**G9. Кодировка, переводы строк, завершающий символ.** Сериализатор пишет `\n` в конце (`parser.ts:156`), парсер режет по `\n` (`parser.ts:116`), про CRLF и кодировку не сказано нигде. Мелочь, но именно такие мелочи агент воспроизводит буквально.

**G10. Что вообще имеет право лежать в папке банка.** Класс `unsupported` (`core.ts:212-224`) описывает поведение редактора («покажем, но не тронем»), но не правило апстрима: допустимы ли в папке банка какие-то ещё файлы и какие. Без этого `format-rules.md` не сможет ответить агенту на вопрос «можно ли создать здесь README».

**G11. Язык самого документа.** Карта #11 держит вопрос языка промта открытым («Not yet specified»: документы русские, агент может быть англоязычным). Все правила выше сформулированы по-русски и цитируют русские источники, тогда как сообщения валидации в коде английские (`validation/index.ts:22, 31, 46, 59, 87, 136`). Для `format-rules.md`, который идёт и в промт, это выбор, а не деталь оформления.

## 8. Итог по составу

Кандидатов в `format-rules.md` — **42 правила**: 11 структурных (§1), 8 по колонкам (§2), 7 по примерам и распознаванию (§3), 11 по файлам банка (§4), 5 по пересечениям (§5, из них X4 отдаём cookbook) — плюс сводная таблица из 9 кодов ошибок (§6).

Из них:
- **32 нигде в cookbook не отражены** — чистое наполнение нового документа;
- **6 покрыты cookbook полностью** (E3, E6, E7, C7, C8, X4) — в `format-rules.md` не дублируем, максимум ссылаемся;
- **4 покрыты косвенно** (F7, C1, C2, C6) — переформулировать под структурную оптику, следя за расхождениями.

**11 открытых вопросов** (§7), из которых блокирующими для написания документа выглядят G1 (senders.txt), G3 (параметры колонок), G4 (пустые колонки как класс) и G6 (многострочный regex) — по ним документ не может быть написан без решения человека, потому что источника правды в репозитории нет.
