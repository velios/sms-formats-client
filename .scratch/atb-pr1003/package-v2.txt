Актуальность: `draft` новее `pr`, `pr` новее `main` — свежайшее намерение автора ищи в самом позднем слое, где файл присутствует.

Выполни задачу из блока `task` и верни ответ той же псевдо-XML, что и запрос: изменённый или новый файл — блоком `<file path="…">` с полным новым телом, без diff и без сокращений; удаление — блоком `<delete path="…">` с причиной одной строкой внутри; переименование — блоком `<rename from="…" to="…">` с причиной одной строкой внутри. Объём работ: по умолчанию меняй только те файлы, которых задача касается прямо. Массовую переделку остальных форматов банка делай только тогда, когда задача просит об этом явно. Когда задача разрешила её явно, убирай дубли объединением форматов: все примеры удаляемого файла до одного переноси в консолидирующий, а сам файл оформляй блоком `<delete>` с причиной. Ни один EXAMPLE не должен пропасть из банка.

Приоритет: прямые указания из блока `task` важнее правил этой легенды.

# Transaction SMS Regex Cookbook

Практический каталог правил, сниппетов и случаев для написания regex в форматах банковских SMS.

**Кто пользуется этим документом:**
1. **Оператор** — выбирает готовые куски regex в редакторе, опираясь на описания случаев и примеры.
2. **Тюнинг промптов бота** — формулировки отсюда можно переносить в системные промпты генератора.

**Главный принцип.** В репозитории сосуществуют два набора соглашений:
- **Современный стандарт** — практика последних ~2 месяцев. Она порождается ботом `scripts/generate_sms_format.py`, который грузит `transaction_sms_entities_extraction_guide.md` и `transaction_sms_regex_writing_guide.md` дословно как системные промпты. То есть свежая практика == гайды by construction.
- **Легаси** — тысячи накопленных файлов со старыми соглашениями. Из легаси **не копируем паттерны**: старые соглашения не становятся образцом оттого, что лежат в соседнем файле банка.

Везде ниже **дефолт = современная практика**. Где письменная формулировка промпта-гайда расходится с практикой, практика идёт дефолтом, а формулировка промпта — альтернативой.

---

## 1. Как это исполняется (механика, без которой сниппеты непонятны)

Конвейер: **классификация** SMS (`ad | failed_transaction | otp | transaction | undefined`) → **извлечение сущностей** (`entities[{name,value}]` + `explanation`) → **генерация regex** → **валидация + до 5 ретраев**.

Что критично для формы regex:

- **Валидатор равенства группы значению.** Каждая capture-группа обязана после `.strip()` **точно равняться** значению сущности (`value`). Для денежных колонок (`income, outcome, fee, cashback, op_income, op_outcome, balance, av_balance`) перед сравнением срезаются **все** пробелы, поэтому `1 000` == `1000`. Это и есть причина, почему числовые группы безопасно включают `\s`, но **не должны** захватывать хвостовую пунктуацию или соседние токены.
- **Флаги по умолчанию выключены.** `compile_regex` компилирует без `IGNORECASE`, `DOTALL`, `UNICODE`. Регистр значим. Есть синтаксис `/pattern/flags` (`i,u,m,s`) — но он не используется ни в одном файле, а инлайн `(?i)` — лишь в ~20. Вывод: на регистронезависимость не полагаемся, пишем якоря в реальном регистре SMS.
- **Примеры схлопываются в одну строку.** `_clean_text` заменяет `[\n\r]+` на пробел и в regex, и в тексте SMS. Поэтому многострочный SMS матчится как одна строка, а `.*` спокойно «перешагивает» видимые переносы.
- **`\d` и `\w` — юникодные** (Python 3 `re`): `\w` матчит кириллицу, `\b` считает границу по кириллической букве. **Но только в апстриме.** В движке регулярных выражений браузера (а значит, в нашем редакторе) `\w`, `\d` и `\b` всегда ASCII, флаг `u` этого не меняет: `Код\b` и `\w` рядом с кириллицей апстрим матчит, а редактор показывает `EXAMPLE_NO_MATCH`. Поэтому рядом с кириллицей вместо `\b` и `\w` берём литеральные якоря из SMS (`Код `, `Код:`) или явные классы (`[А-Яа-я]`, `[\d\s]`) — они одинаково работают в обоих движках.

## 2. Маркеры «легаси ↔ современный стандарт»

Если файл выглядит так — это **старый стиль**, не копируйте из него:

| Признак | Легаси | Современный стандарт |
| --- | --- | --- |
| Начало паттерна | `^Pokupka...` (≈89% старых) | без `^` (≈98% свежих) |
| Числовая группа | end-anchored `([\d\s.,]*\d)` | start-with-digit `(\d[\d\s.,]*)` |
| `av_balance` | `(-?[\d\s.,]*\d)` | `(-?\d[\d\s.,]*)` |
| Валюта (символ/не-ISO) | `([а-яa-zA-Z]{1,3})`, `([A-Z]{3}\|\W)` | `(\S+)` — дефолт; `([A-Z]{3})`/`(\S)` только по триггеру (§3.3) |
| `payee` | `(.*?)` | `(.+?)` |
| Дата | явный формат `date#dd.MM.yyyy` | order-based `date#dMy` |

---

## 3. Каталог сниппетов по сущностям

Для каждой сущности: **дефолт (80%)**, **альтернативы (20%) с условием-триггером**, **легаси — не копировать**, **грабли**.

**Дефолт у сущности ровно один.** Альтернатива берётся только по своему триггеру — причине, наблюдаемой в EXAMPLE текущего формата, — а не «на всякий случай» и не потому, что такая форма частая в корпусе. Правило действует и при правке существующего паттерна: недефолтную форму меняем на дефолт сущности, если триггер альтернативы примерами не подтверждается; оставленную альтернативу объясняем — чем дефолт не подошёл.

### 3.1 Денежные суммы операции — `income`, `outcome`, `fee`, `cashback`, `op_income`, `op_outcome`

**Дефолт (≈60% свежих):**
```
(\d[\d\s.,]*)
```
Начинается с цифры, дальше цифры/пробелы/`.`/`,`. Матчит и целые (`1000`), и дробные (`1000.00`, `1 000,00`). Подходит, когда сумма **может быть без копеек**.

Пример: `... +2,674,000VND vao ...` → `\+?(\d[\d\s.,]*)([A-Z]{3})` захватывает `2,674,000`.

**Альтернатива A — центы обязательны (≈35%):**
```
(\d[\d\s.,]*[.,]\d{2})
```
Триггер: в шаблоне сумма **всегда** с 2 знаками после разделителя, и/или нужна точная правая граница (сразу за суммой идёт не-пробельный токен или ещё цифры). Жёсткий конец `[.,]\d{2}` не даёт захватить лишнее.

**Альтернатива B — центы опциональны, но граница точная:**
```
(\d[\d\s.,]*(?:[.,]\d{2})?)
```
Триггер: нужна аккуратная десятичная граница, но копейки в шаблоне бывают и отсутствуют.

**Легаси — не копировать:** `([\d\s.,]*\d)`, `([0-9][\d\s]*[.,]\d{2})`.

**Грабли:**
- **Знак минус — вне группы.** Если `value` положителен (направление задаёт ключевое слово), а в SMS стоит `-73.66`, минус выносим из захвата: `-?(\d[\d\s.,]*)`. Иначе группа `-73.66` не совпадёт с `value=73.66`.
- Не добавляйте хвостовой `.*`/пунктуацию — валидатор равенства не пропустит.

### 3.2 Баланс — `balance`, `av_balance`

**Дефолт:**
```
(-?\d[\d\s.,]*)
```
Допускает минус (баланс бывает отрицательным), дальше цифры/пробелы/`.`/`,`. Берём, когда не уверены: баланс бывает целым, а разделитель и точность плавают.

**Альтернатива — центы обязательны:**
```
(-?\d[\d\s.,]*[.,]\d{2})
```
Триггер: баланс в шаблоне **всегда** с копейками — так в ≈50% свежих форматов; тогда берём именно этот вариант. Жёсткий конец отрезает хвост (время, валюту, точку) и даёт точную правую границу.

Пример: `Dostupno: 66.26, USD` → `Dostupno:\s*(-?\d[\d\s.,]*[.,]\d{2})\s*,` захватывает `66.26`.

**Легаси — не копировать:** `(-?[\d\s.,]*\d)`, `([\d\s.,]*\d)`.

**Грабли:** если за балансом сразу идёт время (`9141.03 15:43`) — обязательно `[.,]\d{2}` или граница `(?=\s|$|,)`, иначе в баланс утечёт время.

### 3.3 Валюта — `instrument`, `acc_instrument`, `op_instrument`

**Дефолт — любой непробельный токен валюты:**
```
(\S+)
```
Ловит и ISO-код (`USD`, `VND`), и символ/короткий код (`$`, `Rs`, `₸`). Берём, когда не уверены и валюта ограничена пробелом или другим явным разделителем из SMS.

**Альтернатива A — ISO-код из 3 латинских букв:**
```
([A-Z]{3})
```
Триггер: `(\S+)` захватил бы лишнее — валюта склеена с суммой (`2,808,259VND`) или упирается в пунктуацию без пробела, и нужна жёсткая граница. Сам по себе ISO-код в примерах — не причина отступать от дефолта `(\S+)`.

Пример: `... 2,808,259VND.` → `([A-Z]{3})` захватывает `VND` (а `(\S+)` съел бы и точку — валидатор равенства не пропустит).

**Альтернатива B — ровно один символ:**
```
(\S)         # ₽, $, ₴
```
Триггер: символ валюты ровно один.

**Альтернатива C — формулировка промпта-гайда:**
```
(.+?)        # с явным разделителем, который реально есть в SMS
```
Промпт-валидатор советует для не-ISO именно `(.+?)` с разделителем. На практике операторы чаще берут `(\S+)`/`(\S)`; обе формы допустимы — выбор по тому, как ограничен токен в шаблоне.

**Легаси — не копировать:** `([а-яa-zA-Z]{1,3})`, `([A-Z]{3}|\W)`, `([A-Za-z]{1,5})`. Мультискрипт и смешанные литеральные альтернативы (`(?:[A-Z]{3}|[₽р])`) запрещены — это скрытый хардкод.

**Грабли:**
- Порядок «валюта перед суммой» (`Rs 15.00`) — группа валюты идёт в regex до группы суммы, строго по порядку токенов в SMS.
- **Лишний токен между валютой и правым якорем.** Если рядом с валютой стоит дубликат (символ + ISO: `325,69 kr SEK balance:`), `(.+?)` дотянется до якоря через оба токена и захватит `kr SEK`. Ленивость не спасает — между `kr` и `balance:` нет разделителя, на котором матч остановится. Берём `(\S+)` (один пробел-разделённый токен → `kr`) и съедаем дубликат ленивой склейкой: `(\S+).*?balance:`. Сам дубликат не захватываем (он не сущность); хардкодить `SEK`/`[A-Z]{3}` не нужно.

### 3.4 Идентификатор счёта/карты — `syncid`, `syncid#cash`

**Дефолт (≈90% свежих) — последние 4 цифры:**
```
(\d{4})
```
Берётся **только наш** идентификатор (не контрагента). Якорим по маске, захватывая хвост:
```
\*{2,4}(\d{4})        # *1234, **5678, ***2771
\d{4}\*{3}(\d{4})     # 4318***2771  -> 2771
```
Примеры: `Karta *1877.` → `Karta\s+\*(\d{4})`; `4318***2771` → `\d{4}\*{3}(\d{4})`.

**Альтернативы:**
```
(\d+)        # триггер: id — короткий номер целиком, длина не фиксирована
(\d{3,4})    # триггер: в шаблоне встречается и 3, и 4 цифры
```

**`syncid#cash`** — тот же сниппет `(\d{4})`, но колонка `syncid#cash`. Триггер: операция снятия/внесения наличных (ATM, «Naqd yechish», «Podizanje gotovine», «Снятие/Внесение»).

**Грабли:**
- В одном SMS максимум один `syncid` (или один `syncid#cash`).
- Карта контрагента (`на карту **** 4567`) — **не** `syncid`.
- Если id в шаблоне то есть, то нет — **необязательную группу не пишем** (`(?:\*\*(\d{4}))?`): это два разных набора колонок, то есть два формата. См. §6.

### 3.5 Дата операции — `date#<order>`

**Только order-based.** Имя колонки кодирует **порядок** компонентов (нужен для разрешения неоднозначности `01.02` → день/месяц). Длину года, разделитель и сами цифры несёт regex. Одна форма годится и для числового, и для текстового месяца.

| Колонка | Когда | Сниппет |
| --- | --- | --- |
| `date#dMy` | дефолт: день-месяц-год | `(\d{2}[-./]\d{2}[-./]\d{2,4})` |
| `date#yMd` | ISO `2026-05-16` | `(\d{4}-\d{2}-\d{2})` |
| `date#Mdy` | месяц-день-год (US) | `(\d{2}/\d{2}/\d{2,4})` |
| `date#dM` / `date#Md` | без года | `(\d{2}[./]\d{2})` |
| `date#dMy` (текст. месяц) | `17-Mar-25` | `(\d{2}[-. ][A-Za-z]{3}[-. ]\d{2,4})` |

Примеры: `"16-05-2026 04:14"` → `(\d{2}-\d{2}-\d{4})` под `date#dMy` (время `04:14` остаётся вне группы); `26/04/2026` → `(\d{2}/\d{2}/\d{4})`.

**Легаси — не копировать (в пикере не показывать):** явные форматы `date#dd.MM.yyyy`, `date#dd.MM.yy`, `date#yyyy-MM-dd` и т.п. CI их **не отвергает** (после `#` ничего не валидируется), но новые так не создаём.

**Грабли:**
- Время (`HH:mm[:ss]`) всегда вне группы даты. Скипаем его форма-сохраняющим литералом `\d{2}:\d{2}(?::\d{2})?` (ловит и `18:38:20`, и `18:38`) либо ленивой `.*?` до следующего надёжного якоря — в обоих случаях без группы захвата (время не сущность).
- Дата расписания/следующего списания/срока («Следующее списание 10.08.25») — **не** дата операции, не захватываем.

### 3.6 Получатель/контрагент — `payee`

**Дефолт (≈80% свежих) — нежадный захват до явного разделителя:**
```
(.+?)
```
Всегда ограничивайте справа реальным якорем/разделителем из SMS, иначе `.+?` схватит соседнюю сущность.

Более строгие варианты, когда есть чёткая граница:
```
([^,]+?)      # до запятой:  mesto ([^,]+?), dana
([^"]+)       # внутри кавычек:  "([^"]+)"
([A-Z\s]+?)   # до ключевого слова:  ([A-Z\s]+?)(?=\s+chuyen tien)
```
Примеры: `mesto ATM ALTA IGUMAN, dana` → `mesto\s+([^,]+?),`; `"NICE577P>Seoul"` → `"([^"]+)"`.

**Легаси — не копировать:** `(.*?)`, голый `(.*)` без правого якоря.

**Грабли:** `payee` — это контрагент и для прихода, и для расхода. Канал/банк-посредник («через СБП из Альфа Банк») — не `payee`.

### 3.7 Комментарий — `comment`

**Дефолт:**
```
(.+?)
```
с правым якорем, либо привязка к ключевому полю комментария, реально присутствующему в SMS:
```
Сообщение:\s*(.+?)$
Комментар\w*:\s*(.+)
(chuyen tien[^\n]*)      # якорь на ключевую фразу из SMS
```

**Грабли:** **не** тащите в `comment` стабильные якорные слова типа операции («Покупка», «Оплата», «Отмена операции», «Перевод»). `comment` — только переменный пользовательский текст или выделенное поле сообщения.

### 3.8 MCC — `mcc`

```
(\d+)
```
Целое число кода категории мерчанта, по якорю из SMS (`MCC 5411`).

### 3.9 Направление: `income` vs `outcome`

Решается ключевыми словами и знаком (это работа этапа извлечения, но влияет на regex):
- `+` перед суммой или «зачислен/Пополнение/Поступление/credited» → `income`.
- «Покупка/Оплата/Списание/Снятие/debited» → `outcome`.
- Знак `-`/`+` в тексте, если `value` без знака, выносим **вне** capture-группы.

## 4. Склейка и якоря

- **Склейка между якорями:** нежадная `.*?` предпочтительна; голая `.*` допустима, когда дальше есть надёжный якорь. Помните: переносы строк уже схлопнуты в пробел, `.` их перешагивает.
- **Пробелы:** между токенами — `\s+`; одиночный пробел не хардкодим. `\s*` — только по явной причине: EXAMPLE показывают и вариант с пробелом, и вариант без него. «Вдруг пробела не окажется» причиной не считается; при правке паттерна `\s*` без такой наблюдаемой вариации меняем на `\s+`.
- **Опциональные конструкции** (`(?:…)?`, одиночный `?`) — только под вариацию, наблюдаемую в EXAMPLE: есть пример с токеном и пример без него. Опциональность «на всякий случай» расширяет паттерн и провоцирует `cross_match`. Опциональных capture-групп не бывает вовсе — разные наборы сущностей это разные форматы (§5).
- **Якоря — только реальные токены SMS.** Не выдумывайте бренды/глаголы/синонимы, которых нет в тексте (`MIR`, `MASTERCARD`, `Message`, если их нет). Регистр сохраняем (флаги выключены) — либо `[Nn]aqd` для вариативного регистра, как в практике.
- **Переменный хвост — не якорь.** URL с путём и параметрами, идентификаторы сессий, номера операций и прочее, что меняется от SMS к SMS, в паттерн не берём вовсе: поиск подстрочный, хвост можно просто не описывать. Якорим стабильную часть — и только её. Антипример: `https://link\.atb\.su/history` целиком в паттерне ломается на первой же ссылке с другим путём; достаточно `https://link\.atb\.su` или вообще ничего.
- **Обобщение в пределах формы токена:** `RUB` → `[A-Z]{3}` (та же форма), а не `[A-Za-zА-Яа-я]{1,5}` (выдуманные алфавит/длина).
- **Без ведущих/хвостовых `.*`** — поиск и так матчит подстроку; и без `^`/`$` для транзакционных regex.

**Не шире, чем требует EXAMPLE.** Правило действует ровно там, где паттерн пишет автор, и не действует на дефолты каталога:

- **Узость обязательна — всё, что автор пишет сам:** склейка, якоря, кванторы. Берём минимально достаточное по имеющимся EXAMPLE: `\s+` вместо `\s*`, когда пробел в примерах есть всегда; `.*?` вместо `.*`; литеральный якорь вместо класса символов, если токен в примерах не варьируется. Расширять можно только под **наблюдаемую вариацию** — то есть подтверждённую отдельным EXAMPLE.
- **Узость не применяется к дефолтным сниппетам каталога.** Дефолт вставляется как есть, даже если он шире, чем показывает единственный пример: он широк намеренно, чтобы пережить вариации того же шаблона, которых в одном примере не видно. Подрезка дефолта под конкретный пример — типичный способ сломать формат на следующей SMS.
- **Между недефолтными альтернативами каталога** выбираем более конкретную для текущего случая.

## 5. Дискриминаторы формата через lookahead

**Необязательных capture-групп не пишем.** Набор колонок фиксирован для файла — одна строка `COLUMNS` на все его примеры, — поэтому вариация «сущность есть / сущности нет» описывается не `(?:…)?`, а **двумя отдельными форматами**, каждый со своим набором колонок. Чтобы они не ловили примеры друг друга, разводим их негативным lookahead на маркер, уникальный для чужого формата (механика ниже). Практика это уже подтверждает: в корпусе форматы штатно разведены по наличию блока баланса — пара «с балансом» / «без баланса», где в паттерне без баланса стоит `(?!.*ostu)`.

**Разница COLUMNS может быть ошибкой, а не фактом.** Колонки легаси-файла — чей-то старый разбор SMS: кривой regex мог потерять сущность или захватить лишнюю, и тогда два файла с разными `COLUMNS` на деле описывают один шаблон. Прежде чем разводить форматы lookahead'ом, заново выдели сущности из текстов EXAMPLE обоих файлов. Совпали истинные наборы — не разводи, а объединяй: все EXAMPLE до одного — в остающийся файл, `COLUMNS` и regex — по заново выделенным сущностям. Такая консолидация особенно уместна при комплексной проработке форматов банка. Lookahead оставь для наборов, различие которых подтвердилось.

**Маркер перед началом матча — признак слияния, а не разведения.** Если чужой формат отличается только меткой, стоящей **перед** тем местом, где начинается наш матч (`СБП: Перевод …` против `Перевод … ║ СБП`), передний lookahead её не увидит: от стартовой позиции он смотрит только вперёд. Зеркальный lookbehind технически компилируется, но в Python `re` он фиксированной ширины — `(?<!СБП:\s)` рубит ровно один пробел и разваливается на двух, хотя остальной паттерн к пробелам терпим. Такая пара — почти всегда один шаблон, у которого метка канала записана в разных местах: объединяй его по правилу выше, а не разводи.

Иногда два формата начинаются одинаково, а различаются **наличием блока** (баланс `Dostupno:`, спецполе и т.п.): один regex для варианта с блоком, другой — без. Чтобы regex «без блока» не съедал SMS «с блоком», добавляем **негативный lookahead** `(?!...)` на токен, который встречается **только** в чужом формате. Lookahead — это **проверка, а не захват**: в группы он не идёт, на нумерацию не влияет.

**Где ставить — две позиции:**

- **В начало паттерна** — `(?!.*Dostupno:)…`. От стартовой позиции матча `.*` добегает до маркера и проваливает весь матч. Надёжно и просто, но `.*` сканирует всю строку. Берём, когда внутри захватываемого текста маркер мог бы оказаться (напр. в названии мерчанта бывают точки/слова), и локальная привязка ненадёжна.
- **Локально, в конце** — сразу за местом, где блок реально начинается в SMS. Дешевле, читается по месту. **Грабли:** если перед таким lookahead стоит ленивая группа `(.*?)`, она при провале проверки **расширится за блок** и обойдёт его — хвостовой lookahead окажется бесполезен. Чтобы локальная проверка работала, предыдущую группу **ограничиваем так, чтобы она не пересекала блок**: `([^.]+)` вместо `(.*?)`, тогда позиция lookahead фиксирована.

Пример (формат «Oplata» без баланса; вариант с `Dostupno:` — отдельный формат):
```
…([A-Z]{3})\.\s+([^.]+)\.(?!\s*Dostupno:)
```
Место упёрто в первую точку (`[^.]+`), сразу за ней `(?!\s*Dostupno:)`: если впереди блок баланса — матча нет; если конец/другой хвост — regex матчит как обычно.

**Грабли:**
- Маркер-дискриминатор должен быть **уникален для чужого формата** и реально присутствовать в его SMS. Берём якорный вид с разделителем (`Dostupno:` с двоеточием), чтобы не цепляться за слово в произвольном тексте.
- Регистр значим (флаги выключены) — пишем маркер в реальном регистре SMS.
- Lookahead не отменяет правило «без `^` и хвостового `.*`»: это проверка содержимого, а не якорь начала/конца.

## 6. Анти-паттерны (сводно)

Четыре категории **хардкода**, которые ловит промпт-валидатор:
1. Валютные литералы: `(RUB)`, `(₽)`, `(USD)`.
2. Имена мерчантов: `(OZON)`, `(PYATEROCHK)`.
3. Суммы: `(1468,88)`, `(1782)`.
4. Номера карт/счетов: `(8587)`.

Плюс:
5. Порядок групп ≠ порядок `entities`.
6. Поведение regex противоречит `explanation`.
7. Выдуманные альтернативы, которых нет в SMS (бренды, глаголы, метки).
8. Спекулятивное расширение формы токена (алфавит/длина/класс) сверх наблюдаемого.
9. Смешанные литеральные альтернативы валюты `(?:[A-Z]{3}|[₽р])` — скрытый хардкод.
10. `^` в начале и хвостовой `.*` для транзакционных regex.
11. Паттерн шире, чем требуют EXAMPLE, в том, что автор пишет сам (склейка, якоря, кванторы): расширение только под наблюдаемую вариацию — см. §4. На дефолтные сниппеты каталога это не распространяется, их не подрезают под пример.
12. Якорь на переменный хвост (URL с путём/параметрами, id сессии, номер операции): следующая SMS того же шаблона его не повторит — см. §4.
13. Необязательная capture-группа (`(?:…)?`): разные наборы сущностей — это разные форматы со своими `COLUMNS`, разведённые негативным lookahead, — см. §5.
14. Альтернатива вместо дефолта сущности без явного триггера: `([A-Z]{3})` там, где `(\S+)` ничего лишнего не захватывает; `\s*` и опциональные `(?:…)?` без вариации, наблюдаемой в EXAMPLE, — см. §3–4.

# Правила формата

Контракт файлов репозитория [`zenmoney/sms-formats`](https://github.com/zenmoney/sms-formats): из чего состоит файл формата, как называются файлы и папки, что запрещено внутри банка и что с нарушением сделает CI апстрима.

Документ отвечает на вопрос **«правильно ли устроен файл»**. На вопрос «правильно ли написан паттерн» отвечает Cookbook — всё, что требует разбора семантики regex (какой сниппет под сумму, как разводить близкие форматы), живёт там. Здесь только то, что проверяется, не читая паттерн.

**Источники.** Разбор и валидация — `scripts/sms_format.py`, `scripts/sms_format_repository.py`, `scripts/validate.py`. Семантика колонок — `docs/transaction_sms_entities_extraction_guide.md`, `docs/transaction_sms_regex_writing_guide.md`. `README.md` апстрима — обзорная страница, а не спека: по `date#`, по пустым колонкам и по пустому id он расходится с кодом и гайдами (см. раздел «README против кода»). При расхождении верен код.

## 1. Файл формата: структура

Строгая, порядок фиксирован. Парсер апстрима не терпит отклонений: файл, который не разобрался, целиком считается ошибкой `invalid_format`, а прогон `validate.py --fix` **удаляет такой файл**.

```
<regex>

-----COLUMNS-----
<col1>;<col2>;…;<colN>

-----EXAMPLE-----
<пример 1>

-----EXAMPLE-----
<пример 2>
```

| # | Правило |
| --- | --- |
| 1 | **Первая строка — regex, и только он.** Строго одна строка, непустая. Многострочного regex не существует: всё, что ниже первой строки, парсер ждёт уже как пустую строку. |
| 2 | **Вторая строка обязана быть пустой.** Дальше подряд идущие пустые строки допускаются. |
| 3 | Дальше — строка **ровно** `-----COLUMNS-----`. Маркер сравнивается после `strip()`, то есть пробелы вокруг него терпимы, но писать их незачем. Маркер обязателен и встречается один раз. |
| 4 | Сразу за маркером — **одна строка колонок**, разделитель `;`. Может быть пустой (см. «Информационный формат» ниже). |
| 5 | После строки колонок — снова **пустая строка**. |
| 6 | Дальше — одна или больше секций `-----EXAMPLE-----`. Каждая секция: строка маркера, затем текст примера до следующего маркера `-----EXAMPLE-----` или до конца файла. Перед каждым следующим маркером обязательна пустая строка. |
| 7 | **Минимум один пример.** Файл без секций примеров — `invalid_format`. |
| 8 | **Пустой пример запрещён.** Секция, в которой после срезки краёв ничего не осталось, — `invalid_format`, а не молча пропущенная секция. |
| 9 | Ничего другого в файле быть не может: строка на месте, где ждётся маркер `-----EXAMPLE-----`, и не являющаяся им, — ошибка разбора. |

**Кодировка и переводы строк.** Файл читается и пишется как UTF-8. Канонический вид, который производят скрипты апстрима: блоки склеены через `\n\n`, файл заканчивается `\n`, regex и тексты примеров записаны без краевых пробелов.

**Примеры и переносы строк.** Пример может быть многострочным — внутренние переносы хранятся в файле как есть. Перед проверкой пример нормализуется — переносы схлопываются в пробел, края срезаются, — но сам файл при этом не меняется: нормализация есть свойство распознавания, а не хранения. При записи файла примеру срезают только края, переносы внутри сохраняются.

## 2. Колонки

Колонки позиционные: колонка *i* описывает, что означает *i*-я группа захвата regex.

### Закрытый список имён

Ровно 16, всё остальное — ошибка `unknown_column`:

| | | | |
| --- | --- | --- | --- |
| `payee` | `income` | `outcome` | `fee` |
| `cashback` | `op_income` | `op_outcome` | `balance` |
| `av_balance` | `comment` | `instrument` | `op_instrument` |
| `acc_instrument` | `date` | `syncid` | `mcc` |

Смысл каждой сущности — в `transaction_sms_entities_extraction_guide.md`; выбор паттерна под сущность — в Cookbook.

### Синтаксис `#`

Имя колонки может нести параметр после `#`. **Валидируется только часть до `#`**, после `#` не проверяется ничего — CI пропустит любой суффикс, включая устаревший и бессмысленный. Отсюда правило: суффикс выбирается по гайдам, а не по тому, что «прошло валидацию».

Осмысленных параметров два:

| Колонка | Значение | Комментарий |
| --- | --- | --- |
| `date#<порядок>` | Порядок компонентов даты: `date#dMy`, `date#yMd`, `date#Mdy`, `date#dM`, `date#Md` | **Обязательная форма — по гайду сущностей, не по CI.** Голый `date` без параметра неоднозначен (`01.02` — день или месяц?). Формат-строки вида `date#dd.MM.yyyy`, `date#yyyy-MM-dd` — легаси: CI их не отвергает, новые так не пишутся. |
| `syncid#cash` | Операция снятия/внесения наличных | Единственное допустимое значение параметра `syncid`. Значений `ccard`, `checking`, `deposit` в апстриме не существует. |

Обычный `syncid` (без параметра) — идентификатор нашего счёта или карты. В одном SMS не больше одного `syncid` либо одного `syncid#cash`.

### Число и порядок групп

- **Число capture-групп regex обязано точно равняться числу колонок.** Иначе — `group_count_mismatch`. Проверка выполняется на каждом совпавшем примере и включается только при непустой строке колонок.
- **Порядок колонок = порядок capture-групп слева направо**, а он, в свою очередь, повторяет порядок появления сущностей в тексте SMS. Валидатор проверяет только количество — за порядок отвечает автор.
- В счёт идут только фактические группы захвата. `(?:…)`, lookahead и lookbehind на нумерацию не влияют — подробности в Cookbook.

**Набор колонок фиксирован для файла** — одна строка колонок на все его примеры. Поэтому SMS одного банка, различающиеся составом сущностей (с балансом и без, с id и без), описываются **разными форматами** со своими `COLUMNS`, а не одним форматом с необязательными группами. Как развести такие форматы, чтобы они не пересеклись, — в Cookbook.

### Разделитель `;`

Строка колонок режется по `;`, каждый элемент обрезается по краям. **Пустые элементы не выбрасываются**: хвостовой `;`, двойной `;;` или ведущий `;` дают пустое имя колонки, а пустое имя не входит в список допустимых → `unknown_column`. В корпусе апстрима нет ни одного файла с пустым элементом внутри непустой строки колонок.

### Информационный формат

**Полностью пустая строка колонок легальна.** Такой файл описывает SMS, из которого не создаётся транзакция (OTP, отказ операции, реклама). Следствия:

- проверка числа групп выключена — regex может вообще не иметь групп захвата;
- **запрет пересечений действует наравне со всеми** — информационный формат так же не должен ловить примеры чужих форматов банка, и его примеры так же не должны ловиться чужими regex.

В корпусе апстрима таких файлов около 270 из ~6000 — это штатный, а не аварийный класс.

## 3. Regex как содержимое файла

Три свойства, проверяемые без разбора семантики паттерна:

| Правило | Детали |
| --- | --- |
| **Однострочность** | Regex — это ровно первая строка файла. Перенос строки внутрь паттерна не переносится: со второй строки парсер ждёт структуру файла. |
| **Синтаксис** | Паттерн компилируется диалектом Python `re`. Не компилируется — `regex_error`, и формат дальше не проверяется вовсе (ни примеры, ни пересечения). `--fix` такое не чинит. |
| **Флаги** | Поддержан синтаксис `/pattern/flags` с флагами `i`, `u`, `m`, `s`: если первая строка начинается с `/` и содержит ещё один `/`, хвост после последнего `/` читается как флаги. **В корпусе апстрима им не пользуется ни один файл** — по умолчанию флаги выключены и регистр значим. Инлайн-конструкция `(?i)` для Python — часть паттерна и работает; в корпусе она в 20 файлах (см. последний раздел). |

Как писать сам паттерн — Cookbook и `transaction_sms_regex_writing_guide.md`.

## 4. Примеры

| Правило | Ошибка при нарушении |
| --- | --- |
| Каждый пример обязан распознаваться regex **своего** файла | `example_no_match` |
| Каждый пример обязан **не** распознаваться regex любого другого формата **этого же банка** | `cross_match` |
| Минимум один пример на файл | `invalid_format` |

Распознавание — это поиск подстроки по нормализованному тексту примера, а не полное совпадение строки; следствия для паттерна разобраны в Cookbook.

**Пример — расходный материал для `--fix`.** И `example_no_match`, и `cross_match` апстрим чинит одинаково: удаляет провинившийся пример из файла. Если после удаления примеров не осталось — **удаляет файл целиком**. Поэтому формат с единственным примером, который с кем-то пересёкся, исчезает без предупреждения.

### Пример как данные

Правил ниже CI не проверяет — это соглашение, но следовать ему стоит: пример нужен, чтобы формат можно было проверить и починить через год.

- **Пример — дословный текст реальной SMS.** Копируется как пришёл, вместе с исходной пунктуацией, регистром и разделителями. Ничего не выдумывать: regex пишется по якорям из этого текста, и подправленный «для красоты» пример уводит паттерн от того, что банк шлёт на самом деле.
- **Анонимизировать не нужно.** Номера карт банки и так шлют маскированными (`*1234`, `**** 5678`), а суммы, даты и названия мерчантов — часть шаблона, по которой формат опознаётся; вычищенный пример перестаёт быть образцом. Если в тексте оказались избыточные персональные данные (полное ФИО, телефон, полный номер счёта), их можно заменить на правдоподобные — но с сохранением формы токена, иначе regex перестанет матчиться.
- **Сколько примеров.** По одному на каждую наблюдаемую вариацию шаблона: с балансом и без, с комментарием и без, приход и расход, если шаблон один. Примеры-близнецы, отличающиеся только суммой и датой, ничего не проверяют, а риск наступить на `cross_match` с соседним форматом добавляют.
- **Один и тот же текст в двух форматах одного банка невозможен** — он немедленно даст `cross_match` обоим. В разных банках повторение безвредно: проверка ограничена банком.

## 5. Файлы и папки банка

```
src/
  <имя банка>_<id банка>/
    senders.txt
    formats/
      <имя формата>_<id формата>.txt
```

### Что вообще имеет право лежать в папке банка

Список закрытый, всё лишнее CI помечает ошибкой, а `--fix` **удаляет**:

| Место | Разрешено | Ошибка |
| --- | --- | --- |
| Корень папки банка | только `senders.txt` | `invalid_file` |
| Подпапка `formats/` | только файлы `*.txt` | `invalid_extension` |
| Любая другая подпапка банка | ничего | `invalid_file` |

README, заметки, `.json`, картинки в папке банка держать нельзя.

### Имя папки банка

- Форма `<имя>_<id>`, где разделителем считается **последний** символ `_` в имени папки. Всё до него — имя, всё после — id. Пустой id (`Имя банка_`) и имя без `_` — ошибка `invalid_name`, и она **не чинится автоматически**: id из репозитория не выводится.
- Имя банка должно совпадать со своей «чистой» формой: без `?*'"$`, без `/\.{}_()`, без управляющих символов и `<>:"/\|?*`, с одиночными пробелами и без хвостовых точек/пробелов. Символ `_` в чистой форме не выживает: он заменяется пробелом, поэтому имя банка с `_` всегда даёт `invalid_name`, и `--fix` его переименует. Слова разделяются пробелами. Имена, зарезервированные в Windows (`con`, `prn`, `aux`, `nul`, `com1`…`com9`, `lpt1`…`lpt9`), получают приписку ` file`.
- Несовпадение с чистой формой `--fix` исправляет переименованием папки.

### Имя файла формата

- Форма `<имя формата>_<id формата>.txt`, разделитель — последний `_` в имени файла. Пустой id допустим (`Имя формата.txt`) — в отличие от папки банка, наличие id у формата CI не требует.
- **Имя формата не выбирается человеком — оно вычисляется из первого примера** алгоритмом апстрима:
  1. взять первый пример, из которого что-то получается;
  2. заменить все не-словесные символы на пробел, выбросить все цифры, схлопнуть пробелы;
  3. взять первые 50 символов и обрезать края;
  4. привести к «чистой» форме (те же правила, что для имени банка).

  Пример: `Pokupka 1000r VISA5567 AIST-PRESS` → `Pokupka r VISA AIST PRESS`.
- Если имя в файле не равно вычисленному — `invalid_name`, и `--fix` **переименовывает файл**, сохраняя id. То есть любое ручное имя живёт до первого прогона валидации апстрима.
- Символы в имени файла: только буквы (любого алфавита), цифры, пробелы и `_`. Нарушение — `invalid_filename_chars`, и `--fix` **удаляет** такой файл. (Сама проверка в CI смотрит только на начало имени, но полагаться на эту дыру не стоит: имя всё равно будет перезаписано вычисленным.)
- **Id уникален внутри банка** — не проверкой CI, а инвариантом записи: сохраняя формат, апстрим удаляет другие файлы банка с тем же id, а также файл без id, но с тем же именем.

### `senders.txt`

Список источников, от которых приложение может получить сообщение для разбора форматами этого банка: отправитель SMS либо приложение, приславшее push-уведомление. По этому списку сообщение сопоставляется банку — до того, как в дело вступают форматы.

**Механика файла:**

| Правило | |
| --- | --- |
| Один отправитель на строку | Строки обрезаются по краям при чтении |
| Пустые строки игнорируются | |
| **Строка, начинающаяся с `#`, — тоже отправитель** | Комментариев в файле нет и быть не может, `#` — обычный символ идентификатора. Обработки комментариев в коде просто нет; явно сформулировано это только в README |
| Пустой файл легален | Создаётся пустым при заведении банка |
| Кодировка UTF-8, файл заканчивается `\n` | |

Отсутствие самого файла `senders.txt` CI апстрима не проверяет — файл создаётся инструментами при заведении банка. (Наш редактор строже и требует его наличия.)

**Что бывает отправителем.** Проверок на вид идентификатора нет никаких — форма выведена из корпуса (~1300 строк в ~730 банках):

| Вид | Доля | Примеры |
| --- | --- | --- |
| Буквенное имя отправителя SMS | ~2/3 всех строк | `SBERBANK`, `Raiffeisen`, `PSCB-Visa`, `Ваш Тинькофф`, `NH농협` |
| Имя пакета мобильного приложения — источник push | ~1/5 | `com.idamob.tinkoff.android`, `ru.letobank.Prometheus`, `kz.bankffin.app` |
| Короткий номер | ~1/8 | `900`, `2500`, `692632` |
| Телефон в международной форме | ~1/18 | `+37368594666` |

Ограничений на алфавит нет: встречаются латиница, кириллица, корейский и китайский; пробелы, точки, дефисы и подчёркивания внутри идентификатора допустимы. Длина в корпусе — от 2 до 41 символа.

**Соглашения.** Кодом не проверяются, но подтверждены корпусом:

- **Пиши идентификатор ровно так, как его показывает устройство**, с сохранением регистра. Одинаково ли трактуются `BANK` и `bank`, из репозитория не следует — сопоставление отправителя с банком происходит вне его. Поэтому регистр не «нормализуют»: ни приводить к одному виду, ни считать два написания одним отправителем нельзя.
- **Дубликаты внутри файла не нужны** — в корпусе их нет ни одного.
- **Один и тот же отправитель может стоять у нескольких банков** — это норма, а не пересечение: так выглядят процессинги и агрегаторы (`faktura.ru` перечислен у девяти банков). Правило «не пересекаться» относится к regex форматов внутри одного банка и на `senders.txt` не распространяется.
- Пустых строк внутри списка не оставляют, хотя чтение их и переживает.

## 6. Пересечения внутри банка

**Одна SMS не должна распознаваться более чем одним форматом банка.** Это правило уровня банка, и оно самое дорогое в нарушении.

- Проверка идёт **по всем форматам банка**, а не по изменённым: каждый пример каждого формата прогоняется по regex всех остальных форматов **того же банка**. Форматы разных банков друг другу не мешают.
- Информационные форматы (пустые колонки) участвуют наравне со всеми.
- Нарушение — `cross_match`, и `--fix` удаляет пример, из-за которого возникло пересечение, вплоть до удаления файла, оставшегося без примеров.
- Штатный приём разведения близких форматов — негативный lookahead на маркер, уникальный для чужого формата. Разобран в Cookbook.

Локальная валидация в редакторе **не заменяет** проверку апстрима: детали расхождения — в последнем разделе.

## 7. Ошибки валидации апстрима

`validate.py` возвращает список ошибок; `--fix` чинит только часть, остальное остаётся человеку.

| Ошибка | Когда | Что делает `--fix` |
| --- | --- | --- |
| `invalid_format` | Файл не разобрался: нет regex, нарушен порядок блоков или пустые строки, пустой пример, нет примеров | **Удаляет файл** |
| `regex_error` | Regex не компилируется | Ничего |
| `unknown_column` | Имя колонки вне списка из 16 (в том числе пустое имя) | Ничего |
| `group_count_mismatch` | Число групп ≠ числу колонок | Ничего |
| `example_no_match` | Пример не распознаётся своим regex | Удаляет пример; без примеров — удаляет файл |
| `cross_match` | Пример распознаётся regex другого формата банка | Удаляет пример; без примеров — удаляет файл |
| `invalid_name` | Имя файла формата ≠ вычисленному из первого примера; имя папки банка не в форме `Имя_id` или не в чистой форме | Переименовывает файл/папку. Папку банка без id — не чинит |
| `invalid_extension` | В `formats/` файл не `*.txt` | **Удаляет файл** |
| `invalid_file` | В корне банка файл не `senders.txt` либо файл в посторонней подпапке | **Удаляет файл** |
| `invalid_filename_chars` | Недопустимые символы в имени файла формата | **Удаляет файл** |

Соответствие кодам, которые показывает наш редактор:

| Код редактора | Ошибка апстрима |
| --- | --- |
| `MISSING_REGEX`, `MISSING_COLUMNS`, `MISSING_EXAMPLE` | `invalid_format` |
| `INVALID_REGEX` | `regex_error` |
| `INVALID_COLUMN` | `unknown_column` |
| `GROUP_COUNT_MISMATCH` | `group_count_mismatch` |
| `EXAMPLE_NO_MATCH` | `example_no_match` |
| `EXAMPLE_COLLISION` | `cross_match` |
| `MISSING_SENDERS` | нет аналога — проверка только наша |

## Где наше приложение мягче

Редактор — не копия CI апстрима. Четыре известных расхождения; ни одно из них не меняет правил выше — правила задаёт апстрим.

1. **Инлайн-флаг `(?i)` роняет наш редактор.** Regex с `(?i)` компилируется Python'ом и проходит CI апстрима — в корпусе таких файлов 20. Движок регулярных выражений браузера этой конструкции не знает, поэтому редактор показывает такие файлы как `INVALID_REGEX`. Файл при этом корректен; ошибка — наша.

2. **Имя формата у нас вводится руками.** Редактор просит имя при создании формата и не проверяет его. Апстрим имя не спрашивает: он вычислит его из первого примера и при первом же `--fix` переименует файл. Считайте введённое имя черновым.

3. **Зелёная публикация не гарантирует отсутствия пересечений.** Проверка пересечений при публикации считает их только среди **изменённых** файлов, апстрим — по **всем** форматам банка. Формат, пересёкшийся с нетронутым соседом, опубликуется без предупреждения, а `--fix` апстрима удалит провинившийся пример — и файл целиком, если пример был единственным. Полный охват в редакторе даёт отдельный инструмент «Посчитать пересечения».

4. **`\b` и `\w` рядом с кириллицей: здесь редактор строже.** В Python `re` классы `\w`, `\d` и граница `\b` юникодные, в движке браузера — всегда ASCII (флаг `u` этого не меняет). Поэтому `Код\b` перед пробелом или `\w` на месте кириллической буквы в апстриме матчатся, а у нас — нет: файл проходит CI, а редактор показывает `EXAMPLE_NO_MATCH`. Случай зеркальный к `(?i)`: паттерн корректен, ошибка наша. Как писать такие якоря, чтобы совпадали оба движка, — в Cookbook §1.
