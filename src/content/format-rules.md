# Правила файлов формата

Контракт репозитория [`zenmoney/sms-formats`](https://github.com/zenmoney/sms-formats). Семантика regex — в Cookbook; паттерны — в `regex-snippets.toml`. Источники: `scripts/sms_format.py`, `scripts/sms_format_repository.py`, `scripts/validate.py` и `docs/transaction_sms_entities_extraction_guide.md`, `docs/transaction_sms_regex_writing_guide.md`. При расхождении с README верны код и гайды.

## Структура

```text
<regex>

-----COLUMNS-----
<col1>;<col2>;…;<colN>

-----EXAMPLE-----
<пример 1>

-----EXAMPLE-----
<пример 2>
```

Regex — непустая первая строка. За ним пустая строка, один маркер COLUMNS, одна строка колонок (может быть пустой), пустая строка и минимум одна секция EXAMPLE. Маркеры — отдельные строки; пробелы по их краям парсер терпит. Перед следующей секцией нужна пустая строка. Дополнительные пустые строки между блоками допустимы; посторонние строки вне тела примера — ошибка. Пустой после срезки краёв пример запрещён.

Файлы — UTF-8; канонически блоки разделены `\n\n`, файл заканчивается `\n`. Примеры могут быть многострочными. Перед распознаванием рабочая копия проходит схлопывание переводов строк в пробел, срезку краёв и NFC; хранимый текст не изменяется. При записи upstream срезает только края примера.

Импорт SMS отклоняет отдельную строку `-----EXAMPLE-----` (включая пробелы вокруг): это граница секций. Маркер внутри обычной строки допустим, документ при отказе сохраняется.

## Колонки

Закрытый список: `payee`, `income`, `outcome`, `fee`, `cashback`, `op_income`, `op_outcome`, `balance`, `av_balance`, `comment`, `instrument`, `op_instrument`, `acc_instrument`, `date`, `syncid`, `mcc`.

Разделитель — `;`, края каждого имени срезаются. Пустой элемент внутри непустой строки, включая ведущий/хвостовой `;` или `;;`, даёт unknown_column. Полностью пустая строка — информационный формат (OTP, отказ, реклама), без транзакции.

Колонка i соответствует capture-группе i; число групп должно равняться числу колонок, порядок повторяет сущности в SMS. `(?:…)`, lookahead/lookbehind в счёт не входят. При полностью пустых COLUMNS проверка количества выключена, пересечения проверяются.

Набор колонок фиксирован: варианты с сущностью и без неё требуют отдельных форматов, а не необязательных capture-групп.

После `#` CI ничего не проверяет. По гайдам допустимы `date#dMy`, `date#yMd`, `date#Mdy`, `date#dM`, `date#Md` и `syncid#cash`. Дата требует порядка; `date#dd.MM.yyyy` и подобные — легаси. Обычный syncid — наша карта/счёт; максимум один syncid или syncid#cash на SMS. Суффиксов ccard/checking/deposit нет.

## Примеры и распознавание

Пример — реальная SMS в том виде, как её прислал пользователь. Ни пользователь, ни агент не изменяют текст EXAMPLE: запрещены нормализация Unicode, правка пробелов/переносов, анонимизация и замена значений ради regex, имени или валидации. Указания задачи не отменяют это правило. Допустимы перенос между файлами и удаление точных дублей с сохранением копии. Новые вариации подтверждаются отдельными реальными SMS, а не правкой существующего примера.

Редактор проверяет regex, собственные примеры и пересечения на рабочей копии SMS: серии переводов строк заменяются одним пробелом, края срезаются, затем применяется NFC. Исходный EXAMPLE в файле, интерфейсе и этом пакете сохраняется дословно; regex101 получает рабочую копию. Якоря и значения capture-групп проверяй на ней. Например, EXAMPLE «lu + U+0301 + c» распознаётся литералом «lúc»; составную запись EXAMPLE не заменяй. При несовпадении исправляй regex, не EXAMPLE. Механически нормализовать весь regex нельзя: это может изменить смысл классов и квантификаторов. COLUMNS и алгоритм имени файла не нормализуются; имя вычисляется из исходного EXAMPLE.

Python CI получает такой же механизм в [PR #1211](https://github.com/zenmoney/sms-formats/pull/1211): NFC рабочей копии перед проверкой своего regex и пересечений, исходный текст в диагностике. До его мержа CI проверяет без NFC; успешное совпадение в редакторе не гарантирует успех CI. Изменение клиента не меняет мобильный движок Zenmoney.

Каждый пример распознаётся своим regex и никаким другим regex того же банка. Проверка охватывает все пары, включая неизменённые и информационные форматы. Между банками пересечения не проверяются. Один текст в двух форматах банка немедленно создаёт cross_match.

В GitHub Actions regex проверяется Python `re`; поиск подстрочный. `/pattern/flags` читает флаги i,u,m,s после последнего `/`; без флагов регистр значим. Начальный (?i) поддержан редактором, но не обеспечивает полной эквивалентности Python. Различия Unicode-регистра и классов `\w`, `\W`, `\d`, `\b` описаны в Cookbook.

## Файлы банка

```text
src/<имя банка>_<id банка>/
  senders.txt
  formats/<имя формата>_<id формата>.txt
```

В корне разрешён только senders.txt, в formats — только *.txt; других подпапок/файлов нет.

Имя банка и id разделены последним `_`; id обязателен и непустой. Имя должно быть очищено: без `?*'"$`, `/\.{}_()`, управляющих и `<>:"/\|?*`; одиночные пробелы, без хвостовых точек/пробелов. `_` в имени заменяется пробелом. Зарезервированным Windows-именам con/prn/aux/nul/com1…com9/lpt1…lpt9 добавляется ` file`. Апстрим исправляет грязное имя переименованием, отсутствующий id банка — не исправляет.

Имя формата проверяется у всех файлов, с ID и без него: `validate_format_name` сравнивает основу пути с `get_format_name`. Источник — первый EXAMPLE, дающий непустой результат после обработки и обрезки. Алгоритм Python (Unicode, не браузерные `\w`/`\d`):

```python
s = re.sub(r"[^\w]+", " ", example)
s = re.sub(r"\d", " ", s)
s = re.sub(r"\s+", " ", s).strip()
name = clean_name(s[:50].strip())
```

`clean_name` — очистка как у имени банка выше. Если ни один пример не пригоден, используется очищенное текущее имя. `_` переживает обрезку и только затем заменяется пробелом. Не транслитерируй и не дописывай оборванное слово. Например, `Pokupka 1000r VISA5567 AIST-PRESS` → `Pokupka r VISA AIST PRESS`; `Zachislenie BYN Mastercard Kapitalizatciia Dostupno` обрезается до `Zachislenie BYN Mastercard Kapitalizatciia Dostupn`.

Перед ответом проверяй новые и изменяемые файлы. При смене первого пригодного EXAMPLE из-за добавления, перестановки или слияния пересчитай имя; номер не делает его навсегда корректным. Не меняй EXAMPLE ради имени. Суффикс `_ID` отделяется последним `_`, сохраняется при переименовании; у нового файла может отсутствовать — не выдумывай его. Переименование возвращай как новый `<file>` и `<delete>` старого пути. ID уникален внутри банка: запись удаляет другие файлы с тем же ID, а также без ID с тем же именем.

senders.txt: один источник SMS/push на строку, края срезаются, пустые строки игнорируются. Строка с `#` — отправитель, не комментарий. Пустой файл допустим; UTF-8, завершающий `\n`. Идентификатор копируется с устройства с исходным регистром; алфавит/длина не ограничены. Дубли не нужны. Один отправитель у разных банков допустим. Апстрим отсутствие файла не проверяет, редактор требует его.

## Валидация

| Ошибка upstream | Причина | --fix |
| --- | --- | --- |
| invalid_format | Нарушена структура, пустой пример или нет примеров | Удаляет файл |
| regex_error | Regex не компилируется | Не исправляет |
| unknown_column | Неизвестное/пустое имя колонки | Не исправляет |
| group_count_mismatch | Группы не соответствуют колонкам | Не исправляет |
| example_no_match / cross_match | Свой regex не распознаёт пример / чужой распознаёт | Удаляет пример; без примеров удаляет файл |
| invalid_name | Имя не соответствует вычисленному/очищенному | Переименовывает; отсутствующий id банка не исправляет |
| invalid_extension / invalid_file / invalid_filename_chars | Недопустимый файл, расположение, расширение или символы имени | Удаляет файл |

В редакторе MISSING_REGEX/MISSING_COLUMNS/MISSING_EXAMPLE соответствуют invalid_format; INVALID_REGEX — regex_error; INVALID_COLUMN — unknown_column; GROUP_COUNT_MISMATCH — group_count_mismatch; EXAMPLE_NO_MATCH — example_no_match; EXAMPLE_COLLISION — cross_match; MISSING_SENDERS — только локальная проверка.

Поведение upstream `--fix` описано для справки: оно не разрешает удалять уникальные EXAMPLE ради успешной проверки. Исправляй regex или сообщай о несовместимости, сохраняя исходные примеры.

Редактор вводит имя формата вручную и не проверяет его: upstream может переименовать. Проверка публикации охватывает только изменённые форматы, поэтому зелёный результат не подтверждает отсутствие пересечений во всём банке; используй «Посчитать пересечения». Локальная проверка не заменяет upstream.
